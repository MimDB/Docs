# Subscriptions & Filters

This page shows how to connect, subscribe to a table, and receive live change
events. All examples use the browser WebSocket API and plain JavaScript.

## Subscribe to a table

<Steps>

<div>

### Open a connection

Connect to the realtime endpoint for your project. Pass the project's anon key
as the `apikey` query parameter and, once a user is signed in, their JWT as
`token`. The page must be served from an origin listed in
`[realtime].allowed_origins`.

```javascript
const ref = "a1b2c3d4e5f67890";
const apikey = "<anon_key>";
const token = "<user_jwt>"; // optional; omit to connect as anon

const ws = new WebSocket(
  `ws://localhost:9000/v1/realtime/${ref}?apikey=${apikey}` +
    (token ? `&token=${token}` : "")
);

ws.addEventListener("open", () => {
  console.log("Connected to MimDB Realtime");
});
```

</div>

<div>

### Subscribe to a table

Once the connection is open, send a `subscribe` message. Pick any string as
the subscription `id` - you will use it to identify incoming events and to
unsubscribe later. The table needs a primary key and your role needs `SELECT`
on it:

```javascript
ws.addEventListener("open", () => {
  ws.send(JSON.stringify({
    type: "subscribe",
    id: "sub-todos",
    table: "todos",
    event: "*"
  }));
});
```

The server confirms with `{ "type": "subscribed", "id": "sub-todos" }`.

</div>

<div>

### Receive events

Handle the `message` event to process incoming change notifications:

```javascript
ws.addEventListener("message", (e) => {
  const msg = JSON.parse(e.data);

  if (msg.type === "event") {
    console.log(`${msg.event} on ${msg.table}:`, msg.new ?? msg.old);
  }

  if (msg.type === "error") {
    console.error(`Error [${msg.error_code}]: ${msg.message}`);
  }
});
```

</div>

</Steps>

## Row filtering

Add a `filter` field to your subscribe message to receive only events where a
column equals a specific value. The filter format is `column=op.value`.

The only supported operator is `eq` (equality); any other operator is rejected
with `RT-0002`. The comparison is textual: the row value is rendered as a string
and compared with the text after `eq.`, so `zone_id=eq.5` matches an integer
column holding `5` and `active=eq.true` matches a boolean column.

```javascript
// Only receive events for rows where zone_id = 5
ws.send(JSON.stringify({
  type: "subscribe",
  id: "sub-zone-5",
  table: "sensors",
  event: "INSERT",
  filter: "zone_id=eq.5"
}));
```

<Note>
Filters are an optimization that reduces client-side noise. They are evaluated
after the row is re-queried from PostgreSQL under your database role. RLS
policies are the security boundary - a filter cannot expose rows that your
policies hide.

For DELETE events only the primary key columns are available, so a filter on
any other column never matches a delete. Filter on the primary key, or use a
separate unfiltered subscription with `"event": "DELETE"`.
</Note>

## Event types

Subscribe to all operations with `"event": "*"`, or subscribe to a specific
operation:

| Event | `new` | `old` |
|-------|-------|-------|
| `INSERT` | Full new row | `null` |
| `UPDATE` | Full updated row | `null` (the trigger captures the new row only) |
| `DELETE` | `null` | Primary key columns of the deleted row, as strings |

Example: subscribe only to deletes on a `messages` table:

```javascript
ws.send(JSON.stringify({
  type: "subscribe",
  id: "sub-deletes",
  table: "messages",
  event: "DELETE"
}));
```

## RLS enforcement

Every INSERT and UPDATE event passes through Row Level Security before it
reaches your client. When PostgreSQL notifies the hub about a row change, the
hub re-queries the changed row using `SELECT * FROM {table} WHERE {pk}` with
`SET LOCAL ROLE {your_role}`. If the row is not visible under your RLS
policies, the event is silently dropped.

<Warning>
If your RLS policies hide a row from the subscribing client, the INSERT or
UPDATE event for that row is silently dropped - the client receives no
notification. This is intentional: realtime subscriptions expose only what the
client can `SELECT`.

DELETE events are the exception. The deleted row cannot be re-queried, so every
subscriber of the table receives the delete with the row's primary key values,
whether or not RLS would have let them read the row. Do not put sensitive data
in primary keys of tables that end users can subscribe to.
</Warning>

For example, if you have a policy `USING (owner_id = auth.uid())` on a
`documents` table, a client subscribed as user A will only receive events for
documents owned by user A, even if user B inserts a document in the same
table.

See [Row Level Security](/auth/row-level-security) for how to write RLS
policies using MimDB JWT claims.

## Multiple subscriptions

One WebSocket connection supports up to 100 active subscriptions (default,
`max_subscriptions_per_client`). Subscribe to different tables, different event
types, or different filters all on the same connection. Re-using an existing
`id` replaces that subscription instead of adding one:

```javascript
// Subscribe to all changes on two tables
ws.send(JSON.stringify({
  type: "subscribe",
  id: "sub-orders",
  table: "orders",
  event: "*"
}));

ws.send(JSON.stringify({
  type: "subscribe",
  id: "sub-items",
  table: "order_items",
  event: "INSERT"
}));

// Unsubscribe from one when no longer needed
ws.send(JSON.stringify({
  type: "unsubscribe",
  id: "sub-orders"
}));
```

Dispatch events by subscription ID to keep your handlers clean:

<CodeGroup>
```javascript Full example
const handlers = {};

function subscribe(id, table, event, filter, onEvent) {
  handlers[id] = onEvent;
  ws.send(JSON.stringify({ type: "subscribe", id, table, event, filter }));
}

ws.addEventListener("message", (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === "event" && handlers[msg.id]) {
    handlers[msg.id](msg);
  }
});

// Usage
subscribe("sub-todos", "todos", "*", null, (msg) => {
  console.log("Todo changed:", msg.new ?? msg.old);
});

subscribe("sub-active-tasks", "tasks", "INSERT", "status=eq.active", (msg) => {
  console.log("New active task:", msg.new);
});
```
</CodeGroup>
