# Protocol Reference

The MimDB Realtime protocol is a JSON-over-WebSocket message exchange. All
messages in both directions are UTF-8 JSON objects. The `type` field
identifies the message kind.

## Connection

Establish a connection by upgrading HTTP to WebSocket at:

```
ws://localhost:9000/v1/realtime/{ref}?apikey=<jwt_or_api_key>
```

Replace `{ref}` with your 16-character hex project reference. The `apikey` query
parameter accepts either an API key (anon or service_role) or a JWT access
token; a user JWT can also be sent separately as `?token=`. The full credential
order is described in [Realtime](/realtime/overview#authentication).

The server responds with `101 Switching Protocols` on success. On auth,
project, or connection-limit errors the connection is rejected with a JSON
error response before the upgrade completes (see error codes `RT-0100` through
`RT-0300`). Browser connections must also come from an origin listed in
`[realtime].allowed_origins`, otherwise the upgrade itself is refused.

## Message format

Every message is a JSON object. The `type` field is always present. Other
fields depend on the message direction and type.

**Client-to-server fields:**

| Field | Type | Present on |
|-------|------|-----------|
| `type` | string | all messages |
| `id` | string | `subscribe`, `unsubscribe` |
| `table` | string | `subscribe` |
| `event` | string | `subscribe` |
| `filter` | string | `subscribe` (optional) |

**Server-to-client fields:**

| Field | Type | Present on |
|-------|------|-----------|
| `type` | string | all messages |
| `id` | string | `subscribed`, `unsubscribed`, `event`, `error` (when tied to a subscription) |
| `event` | string | `event` |
| `table` | string | `event` |
| `new` | object \| null | `event` |
| `old` | object \| null | `event` |
| `error_code` | string | `error` |
| `message` | string | `error` |
| `server_time` | string | `heartbeat_ack` |

## Subscribe

Send a `subscribe` message to start receiving change events for a table. The
`id` is a client-chosen string that identifies this subscription - use it to
correlate events and to unsubscribe later.

```json
{
  "type": "subscribe",
  "id": "sub-todos-1",
  "table": "todos",
  "event": "*"
}
```

Valid values for `event`: `"INSERT"`, `"UPDATE"`, `"DELETE"`, or `"*"` for
all operations.

The table must satisfy three requirements:

- Its name is a plain identifier (letters, digits, underscores, starting with a
  letter or underscore) of at most 47 characters, so that the derived trigger
  and function names fit PostgreSQL's 63-character identifier limit
  (`RT-0007` otherwise).
- The connection's role has `SELECT` privilege on it (`RT-0003` otherwise).
- It has a primary key. The change trigger encodes the primary key in each
  notification; a table without one fails with `RT-0004`.

The first subscription to a table installs the change trigger. Sending
`subscribe` again with an `id` that is already in use replaces that
subscription.

On success, the server replies with:

```json
{
  "type": "subscribed",
  "id": "sub-todos-1"
}
```

On failure (bad table name, insufficient privileges, subscription limit
reached), the server replies with an `error` message carrying the same `id`.

## Unsubscribe

Cancel a subscription by sending its `id`:

```json
{
  "type": "unsubscribe",
  "id": "sub-todos-1"
}
```

The server confirms with:

```json
{
  "type": "unsubscribed",
  "id": "sub-todos-1"
}
```

## Events

When a subscribed table changes, the server delivers an `event` message.
The `new` and `old` fields contain the full row data (after RLS enforcement).
Row values are encoded the same way as SQL endpoint results: `numeric` columns
arrive as strings that preserve their scale, and `uuid` columns arrive as
hyphenated strings.

**INSERT** - `new` contains the inserted row, `old` is `null`:

```json
{
  "type": "event",
  "id": "sub-todos-1",
  "event": "INSERT",
  "table": "todos",
  "new": {
    "id": 42,
    "task": "Buy groceries",
    "done": false,
    "created_at": "2025-01-01T12:00:00Z"
  },
  "old": null
}
```

**UPDATE** - `new` contains the updated row and `old` is `null`; the trigger
does not capture the previous version of the row:

```json
{
  "type": "event",
  "id": "sub-todos-1",
  "event": "UPDATE",
  "table": "todos",
  "new": {
    "id": 42,
    "task": "Buy groceries",
    "done": true,
    "created_at": "2025-01-01T12:00:00Z"
  },
  "old": null
}
```

**DELETE** - `new` is `null`, `old` contains only the primary key columns,
with every value rendered as a string (the trigger casts the key to text):

```json
{
  "type": "event",
  "id": "sub-todos-1",
  "event": "DELETE",
  "table": "todos",
  "new": null,
  "old": {
    "id": "42"
  }
}
```

Because the row no longer exists there is nothing to re-query, so DELETE events
are delivered to every subscriber of the table regardless of RLS policies.

## Heartbeat

The server sends a WebSocket-level **ping** frame every 30 seconds (default)
to detect dead connections. The underlying WebSocket library handles the
pong response automatically in most client environments.

Outbound messages are buffered per client (`send_buffer_size`, default 256).
A client that reads too slowly to keep the buffer from filling has messages
dropped rather than stalling the hub.

In addition, the MimDB protocol supports an application-level heartbeat for
environments where the WebSocket library does not expose ping/pong:

```json
{ "type": "heartbeat" }
```

The server replies immediately with:

```json
{
  "type": "heartbeat_ack",
  "server_time": "2025-01-01T12:00:00Z"
}
```

<Note>
The server closes the connection if no pong is received within 10 seconds of
a ping. The default heartbeat interval is 30 seconds and the pong timeout is
10 seconds. Both are configurable in `[realtime]` via `heartbeat_interval`
and `pong_timeout`.
</Note>

## Error codes

Errors delivered as JSON messages over the connection (after the WebSocket
upgrade):

| Code | Meaning |
|------|---------|
| `RT-0000` | Invalid message format - the JSON could not be parsed or the type is unknown |
| `RT-0001` | Invalid event type - must be `INSERT`, `UPDATE`, `DELETE`, or `*` |
| `RT-0002` | Invalid filter expression |
| `RT-0003` | Insufficient privileges on the target table |
| `RT-0004` | Subscription setup failed - trigger could not be installed |
| `RT-0005` | Subscription error - row re-query failed |
| `RT-0006` | Hub shutting down - reconnect after a brief delay |
| `RT-0007` | Invalid table name |
| `RT-0008` | Subscription limit reached (default: 100 per client) |

HTTP errors returned before the WebSocket upgrade completes:

| Code | HTTP status | Meaning |
|------|-------------|---------|
| `RT-0100` | 401 | Invalid or expired access token (also returned when a Bearer value is neither a valid JWT nor a valid API key) |
| `RT-0101` | 401 | Token version revoked |
| `RT-0102` | 401 | Invalid API key (also returned when an `apikey` value is neither a valid key nor a valid JWT) |
| `RT-0103` | 401 | API key does not belong to this project, whether it was sent as a Bearer token or as `apikey` |
| `RT-0104` | 401 | Authorization header must use Bearer scheme |
| `RT-0105` | 401 | Unrecognized JWT role (must be `authenticated` or `anon`) |
| `RT-0200` | 404 | Project not found |
| `RT-0201` | 404 | Project not found (project details could not be loaded) |
| `RT-0300` | 503 | Connection limit reached (per project or global) |
| `SYS-0700` | 503 | Server temporarily overloaded (key validation or project database unavailable); retry |
