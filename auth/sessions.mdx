# Sessions

MimDB tracks login sessions in PostgreSQL, allowing users to see where they are
signed in and revoke access from specific devices.

## Session model

A session is created when a user logs in via `POST /v1/auth/{ref}/token` with
`grant_type=password`, or signs in through an OAuth provider. Signup does not
create a session. Each session records:

- The IP address of the client at login time
- The User-Agent string of the client
- A `last_seen_at` timestamp that is updated on every successful token refresh

Sessions are linked to refresh tokens. When a refresh token is rotated, the
session's `last_seen_at` is updated (a change of IP address or User-Agent since
login is logged server-side but never blocks the request). When a refresh token
is revoked (logout), the linked session is deleted.

<Note>
Sessions are stored in the `auth_sessions` table in your project's PostgreSQL
database. They are not stored in Redis and are not affected by cache
configuration.
</Note>

All responses on this page use the standard envelope
`{"data": ..., "error": null, "meta": {"request_id": "..."}}`.

## List sessions

Retrieve all active sessions for the authenticated user. Requires a valid access
token.

<CodeGroup>
```bash Request
curl https://api.example.com/v1/auth/a1b2c3d4e5f67890/sessions \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

```json Response (200 OK)
{
  "data": [
    {
      "id": "01970000-0000-7000-8000-000000000010",
      "user_id": "01970000-0000-7000-8000-000000000001",
      "ip_address": "203.0.113.42",
      "user_agent": "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)...",
      "created_at": "2025-01-01T09:00:00Z",
      "last_seen_at": "2025-01-02T15:30:00Z"
    },
    {
      "id": "01970000-0000-7000-8000-000000000011",
      "user_id": "01970000-0000-7000-8000-000000000001",
      "ip_address": "198.51.100.7",
      "user_agent": "MimDB-Client/1.0",
      "created_at": "2025-01-02T08:00:00Z",
      "last_seen_at": "2025-01-02T08:00:00Z"
    }
  ],
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

Sessions are ordered by `last_seen_at` descending (most recently active first).
`ip_address` and `user_agent` are omitted when they were not captured. `data`
is `null` when the user has no sessions.

Without a valid access token the endpoint returns `401 AUTH-0102` (no
credential) or `401 AUTH-0100` (invalid token); a token issued before a
password change returns `401 AUTH-0101`.

## Logout

Revoke a session by presenting the refresh token to
`POST /v1/auth/{ref}/logout`. The associated session record is deleted and the
refresh token is permanently revoked.

<CodeGroup>
```bash
curl -X POST https://api.example.com/v1/auth/a1b2c3d4e5f67890/logout \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "d9c7a3b2e1f4..."}'
```
</CodeGroup>

Returns **204 No Content** with an empty body on success. The endpoint needs
no `Authorization` header; the refresh token identifies the user. An unknown
refresh token returns `401 AUTH-0105`; presenting an already-revoked token is
idempotent and returns `204`.

<Note>
Logout only revokes the presented refresh token and its linked session. The
access token remains valid until it expires naturally (up to 1 hour by default).
If you need to immediately block access after logout, use the token version
mechanism: a password change (`PUT /v1/auth/{ref}/user` with `password`) or a
password reset increments `token_version`, and every surface then rejects the
old access tokens with a `-0101` error within the version-check cache window
(default 30s).
</Note>

<Tip>
To revoke all sessions for a user at once (e.g., "log out everywhere"), run the
following against the project database with the service role
(`POST /v1/sql/{ref}/execute`): increment `auth_users.token_version`, set
`revoked = true` on the user's rows in `auth_refresh_tokens`, and delete the
user's rows from `auth_sessions`. This is exactly what a password reset does.
</Tip>

For the dashboard project, the `logout` endpoint also reads the refresh token
from the `_mimdb_refresh` cookie when the body omits it, and clears the
`_mimdb_access`, `_mimdb_refresh` and `_mimdb_csrf` cookies. Logins on other
projects never set cookies, so nothing is cleared for them.

## Get current user

Fetch the authenticated user's profile. Requires a valid access token.

<CodeGroup>
```bash Request
curl https://api.example.com/v1/auth/a1b2c3d4e5f67890/user \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

```json Response (200 OK)
{
  "data": {
    "id": "01970000-0000-7000-8000-000000000001",
    "email": "user@example.com",
    "email_confirmed": true,
    "phone_confirmed": false,
    "token_version": 1,
    "app_metadata": {},
    "user_metadata": { "display_name": "Alice" },
    "last_sign_in_at": "2025-01-02T12:00:00Z",
    "created_at": "2025-01-01T00:00:00Z",
    "updated_at": "2025-01-02T12:00:00Z"
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

The access token can also come from the `_mimdb_access` cookie (dashboard
project); the `Authorization` header takes precedence when both are present.

## Update profile

Users can update their own `user_metadata` and password via
`PUT /v1/auth/{ref}/user`. Requires a valid access token. `app_metadata` is
server-controlled and cannot be changed through this endpoint; it is updated
with the service role key via `PATCH /v1/auth/{ref}/users/{userId}` (body
`{"app_metadata": {...}}`, same merge semantics).

<CodeGroup>
```bash Request
curl -X PUT https://api.example.com/v1/auth/a1b2c3d4e5f67890/user \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -H "Content-Type: application/json" \
  -d '{
    "user_metadata": {
      "display_name": "Alice Smith",
      "avatar_url": "https://example.com/avatars/alice.png"
    }
  }'
```

```json Response (200 OK)
{
  "data": {
    "id": "01970000-0000-7000-8000-000000000001",
    "email": "user@example.com",
    "email_confirmed": true,
    "phone_confirmed": false,
    "token_version": 1,
    "app_metadata": {},
    "user_metadata": {
      "display_name": "Alice Smith",
      "avatar_url": "https://example.com/avatars/alice.png"
    },
    "last_sign_in_at": "2025-01-02T12:00:00Z",
    "created_at": "2025-01-01T00:00:00Z",
    "updated_at": "2025-01-02T14:00:00Z"
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

The `user_metadata` value is stored as a JSONB column and merged with the
existing value on each `PUT` using PostgreSQL's JSONB `||` operator. Keys
present in the request payload are added or overwritten, while existing keys
not included in the payload are preserved.

### Change password

The same endpoint accepts a `password` field (at least 8 characters, otherwise
`400 AUTH-0003`). The new password is hashed and the user's `token_version` is
incremented, so every other outstanding access token is rejected with a
`-0101` error and every outstanding refresh token fails with `AUTH-0108`. The
client should sign in again to obtain fresh tokens.

```bash
curl -X PUT https://api.example.com/v1/auth/a1b2c3d4e5f67890/user \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -H "Content-Type: application/json" \
  -d '{"password": "a-new-passphrase"}'
```

`password` and `user_metadata` may be sent together; the response is the
updated user object.
