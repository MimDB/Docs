# JWT Tokens

MimDB issues HS256-signed JWTs for user authentication. Each project has its
own signing secret, so tokens from one project cannot be accepted by another.

## Token structure

A MimDB access token is a standard JWT with the following claims:

| Claim | Type | Description |
|-------|------|-------------|
| `sub` | string | User UUID - the authenticated user's ID |
| `iss` | string | Always `"mimisbrunnr"` |
| `aud` | string[] | Project `ref` as a single-element array (e.g. `["a1b2c3d4e5f67890"]`) |
| `role` | string | Always `"authenticated"` for user tokens |
| `email` | string | User's email address (omitted if not set) |
| `tv` | integer | Token version - incremented on password change, password reset, or revoke-all |
| `app_metadata` | object | Server-controlled metadata (not writable by users; omitted when empty) |
| `user_metadata` | object | User-writable metadata (omitted when empty) |
| `iat` | integer | Issued-at timestamp (Unix seconds) |
| `exp` | integer | Expiry timestamp (Unix seconds) |

Decoded example:

```json
{
  "sub": "01970000-0000-7000-8000-000000000001",
  "iss": "mimisbrunnr",
  "aud": ["a1b2c3d4e5f67890"],
  "role": "authenticated",
  "email": "user@example.com",
  "tv": 0,
  "app_metadata": {},
  "user_metadata": { "display_name": "Alice" },
  "iat": 1735689600,
  "exp": 1735693200
}
```

The token does not carry `email_confirmed`; read it from the `user` object
returned by the auth endpoints or from `GET /v1/auth/{ref}/user`.

The `tv` (token version) claim is the revocation mechanism. When a user
changes their password (`PUT /v1/auth/{ref}/user`) or completes a password
reset, the server increments `token_version` in the database. Two checks then
apply:

- **Access tokens** - every authenticated surface (`/v1/auth/{ref}/user`,
  `/v1/rest/`, `/v1/storage/`, `/v1/sql/`, `/v1/realtime/`) compares the
  token's `tv` against the database value. A stale token is rejected with
  `401` (`AUTH-0101`, `REST-0101`, `STOR-0101`, `SQL-0101` or `RT-0101`,
  "Token version revoked"). The current version is cached for
  `[cache] version_check_ttl` (default `30s`), so revocation takes effect
  within that window.
- **Refresh tokens** - on refresh, the presented token's stored
  `token_version_at_issue` is compared against the current value. A mismatch
  returns `AUTH-0108` (token version mismatch).

## Access token

Access tokens are short-lived JWTs used to authenticate every API request.

**Default TTL:** 1 hour (`access_token_ttl = "1h"` in `[auth]`)

Include the access token as a Bearer header on all requests to data plane routes:

<CodeGroup>
```bash REST API request
curl https://api.example.com/v1/rest/a1b2c3d4e5f67890/todos \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

```bash Realtime subscription
# Browsers cannot set headers on a WebSocket handshake, so the token goes in
# the query string. ?apikey= accepts either an API key or a user access token;
# ?token= carries a user access token alongside the project's anon key.
wscat -c "wss://api.example.com/v1/realtime/a1b2c3d4e5f67890?apikey=<anon_key>&token=eyJhbGci..."
```
</CodeGroup>

A `401` response with code `AUTH-0100` (or the per-surface equivalent
`REST-0100`, `STOR-0100`, `SQL-0100`, `RT-0100`) means the token is invalid or
expired. Catch this error in your application and trigger a token refresh.

## Refresh token

Refresh tokens are long-lived opaque random strings (256 bits of entropy,
hex-encoded) used to obtain new access tokens without re-entering credentials.

**Default TTL:** 30 days (`refresh_token_ttl = "720h"` in `[auth]`)

Refresh tokens are subject to rotation: each use invalidates the current token
and issues a new one in its place. Only the SHA-256 hash is stored in the
database; the raw token is transmitted only at issuance.

**Reuse detection:** If a refresh token that has already been used is presented
again (potential theft scenario), MimDB revokes the entire token family. The
user must log in again to establish a new session.

## Token expiry

When an access token expires, the auth endpoints return `401` with:

```json
{
  "data": null,
  "error": {
    "code": "AUTH-0100",
    "message": "Invalid or expired access token"
  },
  "meta": { "request_id": "01970000-0000-7000-8000-0000000000aa" }
}
```

The standard flow for handling expiry in a client application:

<Steps>

<div>

### Detect the 401

Intercept all responses in your HTTP client. When the status is `401` and
`error.code` ends in `-0100`, trigger a refresh rather than redirecting to
login. A `-0101` code (token version revoked) means the session was revoked
server-side; a refresh will fail with `AUTH-0108`, so send the user to login.

</div>

<div>

### Refresh the access token

<CodeGroup>
```bash Refresh request
curl -X POST "https://api.example.com/v1/auth/a1b2c3d4e5f67890/token?grant_type=refresh_token" \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "<stored_refresh_token>"}'
```

```json Response (200 OK)
{
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "f1e2d3c4b5a6...",
    "expires_in": 3600,
    "user": { "...": "..." }
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

Store the new `access_token` and `refresh_token`. Discard the old values.

</div>

<div>

### Retry the original request

Re-issue the failed request with the new access token attached.

</div>

</Steps>

If the refresh itself fails (`AUTH-0105` unknown token, `AUTH-0106` expired,
`AUTH-0107` revoked, `AUTH-0108` version mismatch), redirect the user to the
login screen.

## Signing key rotation

Rotating a project's signing key is a destructive operation. It is available
through `POST /v1/platform/projects/{id}/api-keys/regenerate`.

<Warning>
Key rotation immediately invalidates all existing API keys (`anon` and
`service_role`). Existing access tokens also become unverifiable and will return
`AUTH-0100` on their next use. All active users will be forced to log in again.
Plan rotations during a maintenance window or notify users beforehand.
</Warning>

Regeneration inserts the new signing key and deactivates every previous key in
the same database transaction; there is no overlap window. The verifier does
try every key that is active for the project, newest first, so tokens signed
with any active key verify - but the regenerate endpoint only ever leaves one
key active. The old secret is marked inactive and is no longer returned by
the API; there is no endpoint that reactivates it.

The `enforce_jwt_issuer` configuration option (`false` by default) controls
whether the `iss` claim is strictly required. When `false`, tokens without an
`iss` claim are accepted, but a token with a wrong (non-empty) issuer is always
rejected. When `true`, every token must carry `iss = "mimisbrunnr"`.
