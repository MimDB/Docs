# API Keys

Every MimDB project is provisioned with two static API keys: an **anon key**
for public frontend use and a **service role key** for trusted server-side code.
Both are JWTs derived from the project's signing secret.

## What are API keys

API keys are HS256-signed JWTs that carry identifying claims but no expiry. The
server distinguishes them from user access tokens by the absence of the `sub`
and `exp` claims. This is also why an API key cannot be sent as a
`Authorization: Bearer` token on the REST, SQL and storage surfaces - the Bearer
path verifies user access tokens, which must carry both claims.

A decoded anon key looks like:

```json
{
  "iss": "mimisbrunnr",
  "aud": ["a1b2c3d4e5f67890"],
  "role": "anon",
  "iat": 1735689600
}
```

A decoded service role key:

```json
{
  "iss": "mimisbrunnr",
  "aud": ["a1b2c3d4e5f67890"],
  "role": "service_role",
  "iat": 1735689600
}
```

Both keys are signed with the project's active HS256 signing secret and scoped
to the project's `ref` via the `aud` claim. They are not stored in the database;
they are derived on-demand from the stored signing key, so
`GET /v1/platform/projects/{id}/api-keys` always returns the current valid keys.

## Anon key

The anon key is intended for use in frontend code and public API calls. When a
request is authenticated with the anon key, the REST layer executes queries as
the `{ref}_anon` PostgreSQL role.

- **Read-only by default.** The `{ref}_anon` role holds `SELECT` on project
  tables and nothing else. `INSERT`, `UPDATE` and `DELETE` through the anon key
  fail with a permission error unless you grant them explicitly per table.
- **Respects Row Level Security.** Any table with RLS enabled and no policy
  permitting the `anon` role returns no rows.
- **Safe to expose in browser code.** It grants only what your grants and RLS
  policies explicitly allow.

## Service role key

The service role key is for trusted backend code: server functions, admin
scripts, background workers, and CI/CD pipelines. When a request is
authenticated with the service role key, the REST layer executes queries as
the `{ref}_service` PostgreSQL role. The service role key is also the
credential for the administrative surfaces: `/v1/sql/{ref}/execute`, bucket
management under `/v1/storage/{ref}/buckets`, and the user admin routes under
`/v1/auth/{ref}/users`.

<Warning>
The service role key bypasses Row Level Security entirely. Never expose it in
browser JavaScript, mobile app binaries, or any client-side code. A leaked
service role key grants unrestricted read and write access to your project's
data.
</Warning>

## Using API keys

Pass the key in the `ApiKey` header (header names are case-insensitive, so
`apikey` works too):

<CodeGroup>
```bash With anon key
curl https://api.example.com/v1/rest/a1b2c3d4e5f67890/todos \
  -H "ApiKey: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

```bash With service role key (server-side only)
curl https://api.example.com/v1/rest/a1b2c3d4e5f67890/todos \
  -H "ApiKey: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

```bash User access token (not an API key)
curl https://api.example.com/v1/rest/a1b2c3d4e5f67890/todos \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```
</CodeGroup>

<Warning>
`Authorization: Bearer <api_key>` with no `ApiKey` header returns `401` on
`/v1/rest/`, `/v1/storage/` and `/v1/sql/` (`REST-0100`, `STOR-0100`,
`SQL-0100`: "Invalid or expired access token"). The Bearer header is for user
access tokens.
</Warning>

When both `Authorization: Bearer` and `ApiKey` are present, the Bearer value is
verified first as a user access token. If that fails, the `ApiKey` header is
validated instead. This is what makes `@supabase/supabase-js` work: it sends
the anon key in both headers, and the user's access token replaces the Bearer
value after sign-in.

The realtime endpoint accepts the key as `?apikey=<key>` on the WebSocket URL
(browsers cannot set headers on a WebSocket handshake), as an `ApiKey` header,
or as a Bearer token.

An API key presented on a project other than the one in its `aud` claim is
rejected with `401` (`REST-0105`, "API key does not belong to this project").

## Retrieving keys

After the initial project creation (which returns both keys in the response),
retrieve them at any time using the platform API. This requires a platform admin
token.

<CodeGroup>
```bash Request
curl https://api.example.com/v1/platform/projects/01970000-0000-7000-8000-000000000001/api-keys \
  -H "Authorization: Bearer <platform_admin_token>"
```

```json Response (200 OK)
{
  "data": {
    "anon_key": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "service_role_key": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

Note that `{id}` in the path is the full UUID project ID, not the short `ref`
used in data plane routes. The platform admin token is either the static
`platform.admin_secret` or a dashboard user's access token; dashboard users
must be an owner or admin of the organization that owns the project.

## Regenerating keys

To rotate the project's signing secret and generate new API keys:

<CodeGroup>
```bash Request
curl -X POST https://api.example.com/v1/platform/projects/01970000-0000-7000-8000-000000000001/api-keys/regenerate \
  -H "Authorization: Bearer <platform_admin_token>"
```

```json Response (200 OK)
{
  "data": {
    "anon_key": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "service_role_key": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```
</CodeGroup>

<Warning>
Regenerating keys rotates the project's underlying HS256 signing secret. The
new key is inserted and every previous key is deactivated in the same
transaction, so the old `anon_key` and `service_role_key` stop working
immediately and all authenticated users must log in again (their access tokens
no longer verify). Update every deployment that uses the old keys before
triggering this operation.
</Warning>

The audit log records an `apikey.regenerated` event linked to the actor who
triggered the rotation. Signing key rotation is an irreversible operation; the
old secret is deactivated in the database and cannot be recovered.
