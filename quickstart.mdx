# Quickstart

In this guide you will start a local MimDB instance, create an organization and
project, then insert and query data through the REST API - all in under 5
minutes.

<Note>
Go 1.25+ and Docker are required. Docker only runs PostgreSQL; the MimDB
server itself runs from source. Install Docker from
[docs.docker.com](https://docs.docker.com/get-docker/) before continuing.
</Note>

## Start the stack

<Steps>

<div>

### Start PostgreSQL

The repository's Makefile starts a PostgreSQL 18 container for development:

```bash
git clone https://github.com/MimDB/Server.git mimisbrunnr
cd mimisbrunnr
make dev-db
```

This runs `postgres:18` as the container `mimisbrunnr-pg` on port 5432 with
user `postgres`, password `dev`, database `postgres`, and a persistent
`mimisbrunnr-pgdata` volume. Use `docker start mimisbrunnr-pg` on later runs.

</div>

<div>

### Configure

Copy the development configuration and turn off the optional sidecars so the
server needs nothing but PostgreSQL:

```bash
cp configs/dev.toml configs/local.toml
```

In `configs/local.toml`, change these values in the existing `[platform]`,
`[redis]` and `[postgrest]` sections (do not add a second copy of a section -
TOML rejects duplicates), then add a new `[rest_engine]` section:

```toml
[platform]
# Protects /v1/platform/* when set. Must be >= 32 characters.
admin_secret = "dev-admin-secret-not-for-production"

[redis]
enabled = false      # falls back to an in-memory cache

[postgrest]
enabled = false      # no PostgREST binary required ...

[rest_engine]        # new section
enabled = true       # ... the built-in REST engine (MimREST) serves /v1/rest instead
```

Every value can also be overridden with an environment variable named
`MIMISBRUNNR_<SECTION>_<KEY>`, for example
`MIMISBRUNNR_PLATFORM_ADMIN_SECRET`. The full reference is
`configs/mimisbrunnr.example.toml`.

</div>

<div>

### Start the server

```bash
go run ./cmd/mimisbrunnr -config configs/local.toml
```

Requires Go 1.25 or later. Database migrations run automatically on first
start, and the API listens on `http://localhost:9000`.

<Note>
The `docker/` directory in the repository contains the production Docker
Compose files (application host and database host as separate stacks). They
are not a local quickstart; see [Self-Hosting](/self-hosting/docker-compose).
</Note>

</div>

<div>

### Verify it's running

The health endpoints confirm each subsystem is up:

<CodeGroup>
```bash
# Liveness check - returns {"status":"ok"} when the server is accepting requests
curl http://localhost:9000/health

# Readiness check - 200 {"status":"ready", ...} when the database is reachable
curl http://localhost:9000/ready
```
</CodeGroup>

`/ready` answers `503` with `"status":"not_ready"` until the database is
reachable; optional dependencies never fail readiness. See [Readiness](/platform/setup-and-info#readiness---get-ready).

</div>

</Steps>

## Create your first project

<Steps>

<div>

### Initialize the platform

On a fresh install, run the one-time setup to create the platform admin user,
the default organization, and the internal platform project:

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/platform/setup \
  -H "Content-Type: application/json" \
  -d '{
    "email": "admin@example.com",
    "password": "your-secure-password"
  }'
```
</CodeGroup>

The response (`201 Created`) includes an `access_token` for the admin user and
an `auth_ref` identifying the internal platform project. Store the
`access_token` - you will use it to authenticate all subsequent platform API
calls. Alternatively, use the `admin_secret` from your configuration as the
Bearer token.

```json
{
  "data": {
    "access_token": "eyJ...",
    "refresh_token": "3f9a...",
    "expires_in": 3600,
    "auth_ref": "a1b2c3d4e5f67890",
    "user": { "id": "...", "email": "admin@example.com", "...": "..." }
  },
  "error": null,
  "meta": { "request_id": "..." }
}
```

All platform and auth responses use this `{"data", "error", "meta"}`
[envelope](/auth/overview#response-envelope).
The examples below show the `data` portion only.

<Note>
Setup can only be called once. Repeat calls return `409 PROJ-0302`. If you need
to reset, stop the server, remove the database container and its volume
(`docker rm -f mimisbrunnr-pg && docker volume rm mimisbrunnr-pgdata` - this
destroys all data) and start over.
</Note>

</div>

<div>

### Create an organization

Organizations group projects under a shared namespace. Create one with your
admin token:

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/platform/organizations \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access_token>" \
  -d '{
    "name": "My Company",
    "slug": "my-company"
  }'
```
</CodeGroup>

The response (`201 Created`) includes the organization `id`. Save it for the
next step. The admin user becomes the organization's owner.

```json
{
  "id": "01970000-0000-7000-8000-000000000000",
  "name": "My Company",
  "slug": "my-company",
  "created_at": "2025-01-01T00:00:00Z",
  "updated_at": "2025-01-01T00:00:00Z"
}
```

</div>

<div>

### Create a project

A project represents an isolated tenant with its own PostgreSQL database, API
keys, and signing key:

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/platform/projects \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access_token>" \
  -d '{
    "org_id": "<org_id>",
    "name": "My App"
  }'
```
</CodeGroup>

The response (`201 Created`) includes the `project` details together with the
`anon_key` and `service_role_key`. The keys can be retrieved again later (next
step), but the `db_connection_string` for direct PostgreSQL access, when
present, is shown only once.

```json
{
  "project": {
    "id": "01970000-0000-7000-8000-000000000001",
    "org_id": "01970000-0000-7000-8000-000000000000",
    "ref": "a1b2c3d4e5f67890",
    "name": "My App",
    "database_name": "a1b2c3d4e5f67890",
    "schema_name": "public",
    "region": "local",
    "status": "active",
    "settings": {},
    "created_at": "2025-01-01T00:00:00Z",
    "updated_at": "2025-01-01T00:00:00Z"
  },
  "anon_key": { "name": "anon", "raw_key": "eyJ...", "...": "..." },
  "service_role_key": { "name": "service_role", "raw_key": "eyJ...", "...": "..." }
}
```

The `ref` is a short identifier (16 hex characters, starting with a letter)
used in all API routes for this project: `/v1/rest/{ref}/...`,
`/v1/sql/{ref}/execute`, etc.

</div>

<div>

### Retrieve API keys later

If you need to retrieve the keys after the initial creation response:

<CodeGroup>
```bash
curl http://localhost:9000/v1/platform/projects/<project_id>/api-keys \
  -H "Authorization: Bearer <access_token>"
```
</CodeGroup>

```json
{
  "anon_key": "eyJ...",
  "service_role_key": "eyJ..."
}
```

</div>

</Steps>

## Insert and query data

With a project created, you can use the auto-generated REST API to interact
with your database. All REST routes are scoped to your project `ref`.

<Warning>
API keys go in the `ApiKey` header. `Authorization: Bearer` is for user access
tokens issued by `/v1/auth/{ref}/token`; an API key sent there on its own is
rejected with `401`. See [API Keys](/auth/api-keys).
</Warning>

<Steps>

<div>

### Create a table

Use the SQL execution endpoint (requires the `service_role_key`) to create a
table in your project's database:

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/sql/<ref>/execute \
  -H "Content-Type: application/json" \
  -H "ApiKey: <service_role_key>" \
  -d '{
    "query": "CREATE TABLE todos (id bigint generated always as identity primary key, task text not null, done boolean default false, created_at timestamptz default now())"
  }'
```
</CodeGroup>

</div>

<div>

### Insert a row

Use the REST API to insert data. The REST API is auto-generated from your
schema - table names map directly to route paths. The anon role holds
`SELECT` only on project tables, so writes need the `service_role_key` (or a
signed-in user's access token, which carries the `authenticated` role):

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/rest/<ref>/todos \
  -H "Content-Type: application/json" \
  -H "ApiKey: <service_role_key>" \
  -d '{"task": "Read the MimDB docs"}'
```
</CodeGroup>

A successful insert returns `201 Created` with no body (the PostgREST
`return=minimal` default). Add `-H "Prefer: return=representation"` to get
the inserted row back.

</div>

<div>

### Allow reads

MimDB enables Row Level Security on every new table, and a table with RLS and
no policies returns no rows to the `anon` and `authenticated` roles - so at
this point a query with the `anon_key` answers `200 []`. Add a policy that
makes the todos readable:

<CodeGroup>
```bash
curl -X POST http://localhost:9000/v1/sql/<ref>/execute \
  -H "Content-Type: application/json" \
  -H "ApiKey: <service_role_key>" \
  -d '{
    "query": "CREATE POLICY \"todos are readable\" ON todos FOR SELECT USING (true)"
  }'
```
</CodeGroup>

`USING (true)` lets every role read every row; see
[Row Level Security](/auth/row-level-security) for policies that scope rows to
the signed-in user before exposing real data.

</div>

<div>

### Query rows

Retrieve rows with filters using query parameters. Reads work with the
`anon_key` now that a `SELECT` policy exists:

<CodeGroup>
```bash
# Get all todos
curl http://localhost:9000/v1/rest/<ref>/todos \
  -H "ApiKey: <anon_key>"

# Filter by column value (eq = equals)
curl "http://localhost:9000/v1/rest/<ref>/todos?done=eq.false" \
  -H "ApiKey: <anon_key>"

# Select specific columns
curl "http://localhost:9000/v1/rest/<ref>/todos?select=id,task,done" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>

```json
[
  {
    "id": 1,
    "task": "Read the MimDB docs",
    "done": false,
    "created_at": "2025-01-01T00:00:00Z"
  }
]
```

</div>

</Steps>
