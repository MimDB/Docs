# REST API

MimDB exposes a full REST API for every project automatically. When you create a
table in your project's schema, it is immediately available as an HTTP endpoint -
no code, no migrations, no deployment required.

<Note>
The REST API is powered by **MimREST**, a PostgREST-compatible REST engine built
natively in Go. MimREST translates HTTP requests into parameterized SQL and
executes them against your project's PostgreSQL database with full RLS
enforcement. It implements the PostgREST query syntax, so `@supabase/supabase-js`
and other PostgREST clients work against it directly.

Compatibility covers the common path - selecting, filtering, ordering,
pagination, embedding, mutations and RPC. It is close but not complete: parts
of the fuller PostgREST surface behave differently or are not implemented.
If you depend on a corner of the specification, test it against your project
rather than assuming it matches.
</Note>

## How it works

Every REST request follows this path:

```
Client
  -> MimDB  (/v1/rest/{ref}/*)
  -> Auth cascade (JWT -> API key)
  -> MimREST  (Go-native, in-process)
  -> pgxpool (direct connection)
  -> PostgreSQL  (project database)
```

**Auth cascade.** MimDB resolves the credential from the `Authorization: Bearer`
and `ApiKey` headers before executing any query (see
[Using API keys](/auth/api-keys#using-api-keys)); a request with neither is
rejected with `401`.

**Role-based execution.** Each request runs within a PostgreSQL transaction with
the appropriate role set via `SET LOCAL ROLE`. Anon key requests run as
`{ref}_anon`, authenticated JWTs as `{ref}_authenticated`, and service role keys
as `{ref}_service`. This ensures Row Level Security policies are enforced at the
database level.

**Claims forwarding.** The full JWT claims (sub, email, app_role, app_metadata,
user_metadata) are set in the `request.jwt.claims` GUC before your query runs.
This makes `auth.uid()`, `auth.role()`, `auth.email()`, and other helper
functions available inside RLS policy expressions.

**Database isolation.** Each project has its own PostgreSQL database, with tables
in the `public` schema. Project databases are fully isolated - there is no
cross-project data access.

## Base URL

All REST endpoints are scoped to a project reference:

```
/v1/rest/{ref}/{table_name}
```

`{ref}` is the 16-character hex identifier assigned when a project is created
(for example, `a1b2c3d4e5f67890`). You can find it in the project creation response or
via `GET /v1/platform/organizations/{orgID}/projects`.

| Segment | Description |
|---------|-------------|
| `/v1/rest/` | MimREST mount point |
| `{ref}` | Project reference (16 hex characters, e.g. `a1b2c3d4e5f67890`) |
| `{table_name}` | PostgreSQL table or view name in the project schema |

**Example base URL** for project `a1b2c3d4e5f67890`:

```
http://localhost:9000/v1/rest/a1b2c3d4e5f67890/
```

`GET /v1/rest/{ref}/` with no table name returns an OpenAPI 3.0 description of
the project's tables.

### Supabase client compatibility

If you are using `@supabase/supabase-js`, it hardcodes REST paths as
`<baseUrl>/rest/v1/<table>`. MimDB also accepts requests at `/rest/v1/*` for
drop-in compatibility. On this route the project ref is derived from the JWT
audience claim (read from the `Authorization` header, or the `apikey` header
when no bearer token is present) rather than the URL path, so the client
library works without modification.

## Authentication

All REST requests pass through the same auth cascade. Include one of the
following credentials:

```bash
# User JWT (from POST /v1/auth/{ref}/token)
Authorization: Bearer <access_token>

# API key (anon or service_role)
ApiKey: <api_key>
```

A present but invalid credential returns `401`; when both headers are present
the Bearer value is tried first and the `ApiKey` header second. See
[Using API keys](/auth/api-keys#using-api-keys) for the full rule and
[Auth](/auth/overview) for obtaining tokens and API keys.

## Response format

**Read operations** (`GET`) return a JSON array, even when the result contains a
single row:

```json
[
  { "id": 1, "name": "Alice" },
  { "id": 2, "name": "Bob" }
]
```

**Single-object reads** can be requested with the
`Accept: application/vnd.pgrst.object+json` header. MimREST returns a JSON
object (not an array) and returns `406` if zero or more than one row matches.

**CSV output** is available with `Accept: text/csv`. MimREST also accepts
`Content-Type: text/csv` on POST for bulk CSV inserts. The first row contains
column headers, followed by data rows. `NULL` is written as an empty field.

**Query plans** are available with `Accept: application/vnd.pgrst.plan+json`.
The response is PostgreSQL's `EXPLAIN (FORMAT JSON)` output for the statement
the request would run. The statement is planned, not executed, so a plan
request for a `DELETE` describes the delete without performing it. Planning
runs under the caller's role, so table privileges and RLS still apply.

**Writes** (`POST`, `PUT`, `PATCH`, `DELETE`) return no body by default:
`POST` answers `201 Created`, the other three answer `204 No Content`. Add the
`Prefer: return=representation` header to receive the affected rows as a JSON
array in the response (`201` for `POST`, `200` otherwise).

**Error responses** follow the PostgREST-compatible format:

```json
{
  "code": "PGRST116",
  "details": "The result contains 0 rows",
  "hint": null,
  "message": "JSON object requested, multiple (or no) rows returned"
}
```

PostgreSQL errors (constraint violations, permission denied, etc.) are forwarded
with their SQLSTATE code, message, detail and hint, so client libraries that
parse PostgREST errors continue to work without modification. The HTTP status
follows the SQLSTATE class: unique and foreign key violations are `409`, not-null
and check violations are `400`, `insufficient_privilege` is `403`, an
`undefined_table` is `404`, a cancelled statement is `504`.

### Engine error codes

| Code | Status | Meaning |
|------|--------|---------|
| `PGRST002` | 503 | The schema cache for the project could not be loaded. Transient; retry. |
| `PGRST100` | 404 | Table or view not found in the schema cache. |
| `PGRST101` | 400 | Invalid filter syntax, unknown column, unknown filter operator, or (with `handling=strict`) an unknown query parameter. Also `405` for `PUT`, `PATCH` or `DELETE` on an RPC route. |
| `PGRST102` | 400 | Invalid `select` syntax, or a bulk insert whose objects do not share the same keys. |
| `PGRST103` | 416 | Unsatisfiable `Range` header or a negative `limit`. |
| `PGRST104` | 400 | Invalid `order` syntax. |
| `PGRST105` | 405 | Method not allowed, including a `PUT` whose filters are not exactly one `eq` per primary key column. |
| `PGRST106` | 406 | Schema not in the exposed list. |
| `PGRST109` | 400 | A `limit` on `PATCH` or `DELETE` without an `order`. |
| `PGRST115` | 400 | `PUT` body primary key values do not match the URL filters. |
| `PGRST116` | 406 | A single object was requested but zero or several rows matched. |
| `PGRST119` | 400 | A spread embed (`...table(...)`) on a to-many relationship. |
| `PGRST124` | 400 | The request touched more rows than `Prefer: max-affected` allows; the `details` field carries the count. |
| `PGRST200` | 400 | No foreign key relationship found for an embed. |
| `PGRST201` | 400 | More than one relationship matches an embed; add a hint. |
| `PGRST202` | 404 | No function matches the name and supplied parameters. |
| `PGRST203` | 300 | Several function overloads match; rename parameters or the function. |
| `PGRST300` | 500 | Query execution failed. |
| `PGRST301` | 504 | Statement timeout exceeded (10 seconds by default, `[rest_engine] statement_timeout`). |
| `PGRST302` | 503 | Connection pool overloaded; retry later. |

## The Prefer header

Request-level behaviour is controlled with the `Prefer` header. Several
preferences can be combined, separated by commas. When the same key is given
more than once, the first value wins; an unrecognised value is ignored.

| Preference | Applies to | Effect |
|------------|------------|--------|
| `return=minimal` (default), `return=headers-only`, `return=representation` | writes | Whether the affected rows are returned. `headers-only` adds a `Location` header on `POST`. |
| `count=exact`, `count=planned`, `count=estimated` | table reads | Puts the total row count in `Content-Range`. See [Pagination](/rest-api/pagination). Not applied on RPC calls. |
| `resolution=merge-duplicates`, `resolution=ignore-duplicates` | `POST` | Upsert behaviour, together with `?on_conflict=`. See [CRUD](/rest-api/crud). |
| `missing=default`, `missing=null` (default) | `POST` with `?columns=` | Whether a column in the `columns` list that a body object omits is written as its column default or as `NULL`. See [CRUD](/rest-api/crud#insert-multiple-rows). |
| `max-affected=N` | `PATCH`, `DELETE`, RPC | With `handling=strict`, rejects the request with `400` (`PGRST124`) if it touches more than `N` rows; for a function call, the rows it returned. `N` may be `0`; a negative value is `400`. An insert is never bounded. |
| `handling=strict`, `handling=lenient` (default) | all | Strict mode rejects unknown query parameters with `400`. |
| `tx=commit` (default), `tx=rollback` | all | Roll the transaction back after running it, so the response shows what would have happened without persisting it. |
| `timezone=<IANA name>` | all | Sets the session time zone and renders `timestamptz` values in that zone. Unknown zones are ignored and UTC is used. |
| `params=single-object` | RPC | Passes the whole request body as one argument. See [RPC](/rest-api/rpc-functions). |

The response carries a `Preference-Applied` header listing the preferences
that were both asked for and meaningful for that request. For example, a
`GET` never reports `return=` because it has no effect on a read, and
`max-affected` is only reported under `handling=strict`, which is what enforces
it. A function call reports `handling=` and `max-affected=` the same way a
table mutation does. When nothing applies the header is omitted.

<Note>
`handling=strict` rejects unknown query parameters. It does not reject a
preference that cannot be honoured; that preference is ignored and left out of
`Preference-Applied`.
</Note>

## Performance

MimREST eliminates the IPC overhead of external REST-to-SQL proxies.
Key performance characteristics:

- **Zero IPC**: queries go directly from Go to PostgreSQL via pgxpool
- **Batch prelude**: the `SET LOCAL` statements (role, search path, JWT claims,
  statement timeout, and for writes the project ref and application name) and
  the application query are sent in a single pgx batch round-trip
- **No per-project process**: no sidecar memory footprint or cold start latency
- **Schema cache**: table/column metadata cached with LISTEN/NOTIFY invalidation
- **Row cap**: a single response returns at most `max_rows` rows (1000 by
  default, `[rest_engine] max_rows`). The cap is applied in the SQL `LIMIT`, so
  the database is never asked for more rows than can be returned
