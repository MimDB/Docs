# RPC Functions

Any PostgreSQL function created in your project's schema is automatically
callable over HTTP via the RPC endpoint. This lets you run complex server-side
logic, aggregations, or multi-step operations in a single request.

## What are RPC functions

MimDB's REST API exposes PostgreSQL functions at:

```
POST /v1/rest/{ref}/rpc/{function_name}
```

Functions can also be called via `GET` (or `HEAD`), with the arguments passed
as query string parameters:

```
GET /v1/rest/{ref}/rpc/{function_name}?arg1=value1&arg2=value2
```

The function must exist in the project's schema (the schema MimDB provisions for
your project). For `POST` requests, parameters map directly to the JSON body of
the request. For `GET` and `HEAD` requests, parameters are passed as query
string values; a repeated parameter keeps its last value. The return value is
serialised as the HTTP response body.

`GET` and `HEAD` always run the function inside a read-only transaction,
whatever its declared volatility. A `VOLATILE` function that writes has the
write refused by PostgreSQL when called this way and the response is `405`
with SQLSTATE `25006` (`read_only_sql_transaction`), so use `POST` for any
function that modifies data. `OPTIONS /rpc/{function_name}` reports
`Allow: POST, OPTIONS` for volatile functions and
`Allow: GET, HEAD, POST, OPTIONS` for `STABLE` and `IMMUTABLE` ones. `PUT`,
`PATCH` and `DELETE` are rejected with `405` (`PGRST101`).

`Prefer: handling=strict, max-affected=N` bounds a function call by the rows
it returns, on `GET` and `POST` alike: a call returning more than `N` rows is
answered with `400` (`PGRST124`) and anything it wrote is rolled back. See
[the Prefer header](/rest-api/overview#the-prefer-header).

<Note>
RPC functions run inside MimREST's connection, which uses the caller's
PostgreSQL role. Row Level Security policies and `current_setting` JWT claims are
active for the duration of the function call, exactly as they are for regular
table reads and writes.
</Note>

## Creating a function

Use the SQL execution endpoint to create a function in your project's schema.
This requires a `service_role` API key or a `service_role` JWT.

<Steps>

<div>

### Write the function

Write a PostgreSQL function using standard SQL. This example counts incomplete
todos and returns the result as an integer:

```sql
CREATE OR REPLACE FUNCTION count_pending_todos()
RETURNS integer
LANGUAGE sql
STABLE
AS $$
  SELECT count(*)::integer FROM todos WHERE done = false;
$$;
```

</div>

<div>

### Create it via the SQL endpoint

Send the `CREATE FUNCTION` statement to `POST /v1/sql/{ref}/execute`:

<CodeGroup>
```bash cURL
curl -X POST "http://localhost:9000/v1/sql/a1b2c3d4e5f67890/execute" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <service_role_key>" \
  -d '{
    "query": "CREATE OR REPLACE FUNCTION count_pending_todos() RETURNS integer LANGUAGE sql STABLE AS $$ SELECT count(*)::integer FROM todos WHERE done = false; $$;"
  }'
```
</CodeGroup>

A successful response returns `200 OK` with an empty result set.

</div>

<div>

### Call the function

Once created, the function is immediately available at the RPC endpoint (the
schema cache is invalidated by a DDL event trigger, so no reload is needed):

<CodeGroup>
```bash cURL
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/count_pending_todos" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <anon_key>" \
  -d '{}'
```
</CodeGroup>

**Response**

```json
3
```

</div>

</Steps>

## Calling a function

Send a `POST` request to `/v1/rest/{ref}/rpc/{function_name}` with a JSON object
whose keys match the function's parameter names, or use `GET` with query
parameters.

<CodeGroup>
```bash No parameters (POST)
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/count_pending_todos" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <anon_key>" \
  -d '{}'
```

```bash No parameters (GET)
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/count_pending_todos" \
  -H "ApiKey: <anon_key>"
```

```bash With parameters (POST)
# Function: add_todo(task text, priority int) RETURNS void
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/add_todo" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <anon_key>" \
  -d '{
    "task": "Review PR",
    "priority": 1
  }'
```

```bash With parameters (GET)
# Function: get_todo(todo_id int) RETURNS todos
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/get_todo?todo_id=42" \
  -H "ApiKey: <anon_key>"
```

```bash Returning a table
# Function: active_todos() RETURNS SETOF todos
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/active_todos" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <anon_key>" \
  -d '{}'
```
</CodeGroup>

**Response for table-returning function**

```json
[
  { "id": 1, "task": "Read the MimDB docs", "done": false, "created_at": "2025-01-01T12:00:00+00:00" },
  { "id": 3, "task": "Write unit tests",    "done": false, "created_at": "2025-01-02T09:00:00+00:00" }
]
```

### How arguments are matched

Arguments are passed by name and cast to the parameter's declared type in SQL,
so JSON numbers keep their exact text and PostgreSQL decides whether a value
fits. A parameter you omit keeps its SQL `DEFAULT`. An array parameter takes a
JSON array (`{"tags": ["a", "b"]}`) in a `POST` body, or PostgreSQL's array
literal (`?tags={a,b}`) in a query string.

Other ways to supply arguments:

| Body | Behaviour |
|------|-----------|
| JSON object | Each key is matched to a parameter by name |
| JSON array | Values are passed positionally, in declaration order |
| `Content-Type: text/plain`, `text/xml` or `application/octet-stream` | The raw body is passed as the single argument of a one-parameter function |

**Overloads.** When several functions share a name, the one whose parameters
match the supplied argument names (or, for a positional call, the argument
count) is called. If no overload matches, the response is `404` (`PGRST202`)
and the message names the parameters that were searched for. If more than one
overload matches - for example two overloads that differ only by parameter
type - the response is `300` (`PGRST203`); rename the parameters or the
function so the call is unambiguous.

## Passing a single JSON argument

If your function accepts a single `json` or `jsonb` parameter, you can send the
`Prefer: params=single-object` header to pass the entire request body as that
one argument instead of mapping individual keys to parameters.

<CodeGroup>
```bash Single JSON argument
# Function: process_payload(data jsonb) RETURNS jsonb
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/process_payload" \
  -H "Content-Type: application/json" \
  -H "Prefer: params=single-object" \
  -H "ApiKey: <anon_key>" \
  -d '{
    "action": "archive",
    "ids": [1, 2, 3]
  }'
```
</CodeGroup>

Without the header, MimREST would look for parameters named `action` and
`ids`. With `Prefer: params=single-object`, the entire `{"action":"archive","ids":[1,2,3]}`
object is passed as the `data` argument. The response echoes
`Preference-Applied: params=single-object`.

## Return types

MimREST handles each PostgreSQL return type differently:

| Return type | HTTP response | Notes |
|-------------|--------------|-------|
| Scalar (`integer`, `text`, etc.) | JSON primitive | `3`, `"hello"` |
| `SETOF <scalar>` | JSON array of primitives | `[1, 2, 3]` |
| `void` | `204 No Content` | No response body |
| `record`, composite type, or `OUT` parameters | JSON object | `{"col": value, ...}` |
| `SETOF <table>` | JSON array of objects | Same format as `GET` on the table |
| `TABLE(...)` | JSON array of objects | Every row is an object, including a single-column `TABLE(id int)` (`[{"id": 1}, {"id": 2}]`) |
| `json` / `jsonb` | Raw JSON value | Passed through as-is |

`Accept: application/vnd.pgrst.object+json` works on RPC calls too: the result
must be exactly one row, which is returned as an object rather than an array
(`406`, `PGRST116`, otherwise).

Functions returning `SETOF` or `TABLE(...)` support the full query interface: you
can `select` columns, filter, order, and paginate the results using the same
query parameters as table reads. On `POST`, every query parameter other than
`select`, `order`, `limit` and `offset` is a filter on the result. On `GET` and
`HEAD`, a query parameter whose value starts with a filter operator
(`id=gt.3`) is a filter and any other parameter is a function argument. The
server row cap (`max_rows`, 1000 by default) applies to the result set.

<CodeGroup>
```bash Paginate and filter a set-returning function
curl -X POST "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/rpc/active_todos?done=eq.false&order=created_at.desc&limit=5" \
  -H "Content-Type: application/json" \
  -H "ApiKey: <anon_key>" \
  -d '{}'
```
</CodeGroup>

<Note>
`Prefer: count=` is not applied to RPC calls and no `Content-Range` header is
returned. The preferences an RPC call reads are `params=single-object`,
`tx=rollback` and `timezone=`, and those are the only ones it reports in
`Preference-Applied`.
</Note>

## Security

**Role execution.** Functions run under the PostgreSQL role resolved from the
caller's credential (the same role used for table access). RLS policies apply to
any tables the function queries.

**SECURITY INVOKER vs SECURITY DEFINER.**

| Attribute | Behaviour |
|-----------|-----------|
| `SECURITY INVOKER` (default) | Function runs as the caller's role. RLS policies apply normally. |
| `SECURITY DEFINER` | Function runs as the role that defined it (typically a privileged role). RLS is bypassed for that role's tables. |

<Note>
Use `SECURITY DEFINER` with care. Because the function runs as its owner's role,
it can bypass Row Level Security on any table that role can access. Prefer
`SECURITY INVOKER` for functions that should respect the caller's permissions.
When `SECURITY DEFINER` is necessary (for example, to insert into an audit log
that users cannot modify directly), explicitly set the `search_path`:

```sql
CREATE FUNCTION my_func() RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$ ... $$;
```

Setting an empty `search_path` prevents search-path injection attacks.
</Note>
