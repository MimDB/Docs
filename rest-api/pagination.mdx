# Pagination & Ordering

MimDB's REST API provides three pagination strategies: limit/offset, Range
headers, and keyset (cursor) pagination. Ordering is controlled through a query
parameter and applies independently of the pagination method used.

## Ordering

Use the `order` query parameter to sort results. The value is a comma-separated
list of `column.direction` pairs.

| Value | SQL equivalent |
|-------|---------------|
| `?order=created_at.desc` | `ORDER BY created_at DESC` |
| `?order=name.asc` | `ORDER BY name ASC` |
| `?order=priority.desc,name.asc` | `ORDER BY priority DESC, name ASC` |

<CodeGroup>
```bash Single column, descending
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?order=created_at.desc" \
  -H "ApiKey: <anon_key>"
```

```bash Multiple columns
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/tasks?order=priority.desc,name.asc" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>

**Null handling** - Append `nullsfirst` or `nullslast` to control where `NULL`
values appear:

<CodeGroup>
```bash Nulls last
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/products?order=price.asc.nullslast" \
  -H "ApiKey: <anon_key>"
```

```bash Nulls first
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/products?order=price.desc.nullsfirst" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>

A direction is optional and defaults to ascending. Any modifier other than
`asc`, `desc`, `nullsfirst` or `nullslast` is rejected with `400` (`PGRST104`);
ordering by a column that does not exist is rejected with `400` (`PGRST101`).

## Limit and offset

The `limit` and `offset` query parameters mirror SQL `LIMIT` and `OFFSET`.

<CodeGroup>
```bash First page (10 rows)
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?limit=10&offset=0&order=id.asc" \
  -H "ApiKey: <anon_key>"
```

```bash Second page
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?limit=10&offset=10&order=id.asc" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>

`limit=0` returns an empty page. A negative `limit` is rejected with `416`
(`PGRST103`); a negative `offset` is treated as `0`.

<Warning>
Large `offset` values force PostgreSQL to scan and discard all preceding rows
before returning results. On tables with millions of rows, `OFFSET 100000` can
be significantly slower than the equivalent keyset query. Use keyset pagination
for deep pages.
</Warning>

### Server row cap

A single response never contains more than `max_rows` rows (1000 by default,
configured under `[rest_engine] max_rows`). The cap is applied to the SQL
`LIMIT`, so a request with no `limit`, or a `limit` larger than the cap, is
narrowed to the cap. A `limit` smaller than the cap is left alone. The cap also
applies to set-returning RPC functions.

## Range headers

Instead of `limit` and `offset`, you can use the HTTP `Range` header to request
a range of rows, zero-based and inclusive at both ends. MimREST responds with a
`Content-Range` header indicating the rows returned and the total count.

<CodeGroup>
```bash Request rows 0-9 (first 10)
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?order=id.asc" \
  -H "ApiKey: <anon_key>" \
  -H "Range: 0-9"
```

```bash Request rows 20-29
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?order=id.asc" \
  -H "ApiKey: <anon_key>" \
  -H "Range: 20-29"
```
</CodeGroup>

An optional `items=` prefix is accepted (`Range: items=0-9`), and the end may be
omitted to read from the start row to the end of the result, subject to the
server row cap (`Range: 10-`). A malformed header is rejected with `416`
(`PGRST103`).

**Response headers:**

```
Content-Range: 0-9/*
```

The format is `{first}-{last}/{total}`. `{first}` and `{last}` are the
zero-based positions of the first and last row returned. The total is `*`
unless a count was requested with `Prefer: count=` (see below). When the
response contains no rows, the range part is also `*`:

| Situation | `Content-Range` |
|-----------|-----------------|
| Ten rows, no count requested | `0-9/*` |
| Ten rows, `count=exact`, 47 match | `0-9/47` |
| No rows match, `count=exact` | `*/0` |
| No rows, no count (or an offset past the end) | `*/*` |

The response status is `200 OK` whether or not the range covers the whole
result; MimREST does not use `206 Partial Content`. The `Content-Range` header
is also present on `GET` responses that did not send a `Range` header.

If both `Range` and `limit`/`offset` are given, the rows served are the overlap
of the two windows. Two windows that do not overlap are rejected with `416`
(`PGRST103`).

To detect the end of data: if `{last}` in `Content-Range` is less than
`{first} + page_size - 1`, or the range part is `*`, you have received the
final page.

## Count modes

By default MimREST does not compute the total row count (it is expensive
for large tables). You can request a count by adding a `Prefer: count=...`
header.

| Prefer value | PostgreSQL operation | Speed |
|-------------|---------------------|-------|
| `count=exact` | `count(*) OVER ()` in the same statement | Slowest - always accurate |
| `count=planned` | Query planner estimate (`EXPLAIN`) | Fast - may differ from actual |
| `count=estimated` | Exact while the matching rows fit under `max_rows`, otherwise the planner estimate | Balanced |

<CodeGroup>
```bash Exact count
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos" \
  -H "ApiKey: <anon_key>" \
  -H "Prefer: count=exact" \
  -H "Range: 0-9"
```
</CodeGroup>

**Response headers** (exact count):

```
Content-Range: 0-9/47
Preference-Applied: count=exact
```

Use `count=exact` for UI pagination controls where a precise total is required.
Use `count=planned` or `count=estimated` for infinite-scroll UIs where an
approximate count is acceptable. If the estimate query fails, the request still
succeeds and the total is reported as `*`.

`HEAD` requests return the same `Content-Range` header without a body, which is
the cheapest way to fetch a count alone. Counts apply to table reads only; a
`Prefer: count=` on an RPC call is ignored.

## Keyset pagination

Keyset (cursor-based) pagination avoids `OFFSET` by using a filter on the last
seen row's key. It is efficient regardless of how deep into the dataset you
paginate because PostgreSQL can use an index to seek directly to the start of
each page.

<Tip>
Keyset pagination is the recommended approach for datasets with more than a few
thousand rows. It runs in O(log n) time per page rather than O(n) for offset
pagination.
</Tip>

**Pattern:** always include `order` and a filter on the key column:

<CodeGroup>
```bash First page
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?limit=10&order=id.asc" \
  -H "ApiKey: <anon_key>"
```

```bash Next page (id > last seen id)
# Last row on the previous page had id=10
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?id=gt.10&limit=10&order=id.asc" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>

**Response** (first page):

```json
[
  { "id": 1, "task": "...", "done": false },
  ...
  { "id": 10, "task": "...", "done": true }
]
```

To fetch the next page, take the `id` of the last row (`10`) and use
`?id=gt.10`. Repeat until the response contains fewer rows than `limit`, which
signals the final page.

For descending order or composite keys, adjust the direction and filter
accordingly:

<CodeGroup>
```bash Descending keyset (newest first)
# First page
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?limit=10&order=id.desc" \
  -H "ApiKey: <anon_key>"

# Next page (id < last seen id, e.g., 91)
curl "http://localhost:9000/v1/rest/a1b2c3d4e5f67890/todos?id=lt.91&limit=10&order=id.desc" \
  -H "ApiKey: <anon_key>"
```
</CodeGroup>
