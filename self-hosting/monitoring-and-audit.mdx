# Monitoring & Audit

MimDB exposes Prometheus metrics, structured JSON logs, a partitioned audit
log for forensic event tracking, and an in-process monitoring subsystem with a
log viewer, alerting and a public status page.

## Prometheus metrics

`GET /metrics`

Prometheus metrics are disabled by default. Enable them in your config:

```toml
[metrics]
enabled = true
per_project = false
```

When enabled, `/metrics` returns standard Prometheus text format. All metric
names are prefixed with `mimdb_`. When disabled, `/metrics` returns `404`.

### Per-project metrics

When `per_project = true`, the following additional metrics are registered with
a `project_ref` label:

| Metric | Type | Description |
|--------|------|-------------|
| `mimdb_project_ws_connections_active` | Gauge | Active WebSocket connections per project |
| `mimdb_project_ws_events_total` | Counter | WebSocket events per project by `event_type` |

<Note>
Per-project metrics add a high-cardinality `project_ref` label. For small
installs (under ~100 projects), this is manageable. For larger deployments,
disable `per_project` to avoid Prometheus scrape performance issues and
label cardinality explosions.
</Note>

### Prometheus scrape config

Add to your Prometheus `scrape_configs`:

```yaml
- job_name: mimdb
  scrape_interval: 15s
  static_configs:
    - targets: ['127.0.0.1:9000']
  metrics_path: /metrics
```

The repository ships example Prometheus alerting rules for the pooler metrics
in `docker/configs/prometheus-alerts.yml`.

### Stored samples vs the scrape endpoint

`/metrics` serves raw Prometheus format: counters and histograms accumulate
from process start, and a Prometheus server applies its own `rate()` or
`histogram_quantile()` windowing at query time.

The built-in sampler (see Monitoring subsystem below), which writes the same
metrics into `_metering.system_metrics` for the dashboard and alert
evaluator, does that windowing up front instead. Each stored sample describes
one sampling interval rather than all of history:

- **Counters** are stored as the increase since the previous tick.
- **Histograms** are stored as `_p50`, `_p95`, and `_p99` computed over
  only the observations recorded during that tick. A lifetime quantile
  would barely move during a latency spike on a long-running process,
  which makes it unusable for alerting.
- **Gauges** are stored verbatim, since a gauge already represents a
  current value.

An interval in which a series received no observations produces **no
stored sample**. Writing a zero would read as "0s latency" and repeating
the previous value would report stale data as current, so the sampler
records nothing and the alert evaluator skips that tick. Expect gaps in
stored histogram series for endpoints that receive intermittent traffic -
this is normal, and queries against `_metering.system_metrics` should
tolerate them.

## Audit logging

MimDB records a forensic audit trail for security-significant mutations.
Audit events are stored in the `_mimisbrunnr.audit_log` table in the platform
database, which is partitioned by month.

### What is logged

| Event action | Trigger |
|--------------|---------|
| `org.created` | Organization created |
| `project.created` | Project provisioned |
| `apikey.regenerated` | API key rotation |
| `team.invitation_created`, `team.invitation_accepted`, `team.invitation_revoked` | Organization invitations |
| `team.member_role_updated`, `team.member_removed` | Organization membership changes |
| `user.created` | Auth user signup |
| `user.logged_in` | Successful login |
| `token.refreshed` | Refresh token exchanged |
| `session.ended` | Logout |
| `session.revoked` | Session revoked by the user or an admin |
| `user.updated`, `user.password_updated`, `user.app_metadata_updated` | Profile, password and admin metadata changes |
| `password.reset_requested`, `user.password_reset` | Password reset flow |
| `bucket.created`, `bucket.updated`, `bucket.deleted` | Storage bucket lifecycle |
| `object.uploaded`, `object.replaced`, `object.deleted` | Storage object lifecycle |
| `custom_domain.created`, `custom_domain.verified`, `custom_domain.deleted` | Custom domain lifecycle |
| `custom_domain.cf_create_failed`, `custom_domain.cf_delete_failed`, `custom_domain.cf_id_save_failed` | Cloudflare for SaaS call failures |
| `function.deployed`, `function.deleted` | Edge function lifecycle |
| `extension.enabled`, `extension.disabled` | Per-project extension toggles |

Each event records the request ID, actor ID and role, project ref, client IP
(honouring `[rate_limit].trusted_ip_header`) and action-specific metadata.

### Durability tiers

Audit events use two durability tiers:

| Tier | Method | Behavior |
|------|--------|----------|
| **Critical** | Synchronous | Written inside the mutation's own transaction. If the audit write fails, the entire mutation rolls back and the request returns `SYS-0601` - the operation never completes without an audit record. |
| **Operational** | Asynchronous | Buffered (1000 events) and written in batches of up to 50 by a background writer. If the buffer is full, the event is written to the structured log instead and `mimdb_audit_events_dropped_total` increments. The mutation completes regardless of buffer state. |

The critical tier is used for `org.created`, `project.created`,
`apikey.regenerated`, `bucket.deleted` and `object.deleted`. Everything else,
including all auth events, uses the asynchronous tier: auth mutations run in
a transaction on the project database while the audit table lives in the
platform database, so they cannot share a transaction.

### Partitioning

The `audit_log` table is range-partitioned by `created_at` with monthly
partitions. Partition names follow the pattern `audit_log_2025_01`.

<Note>
Partitions must exist before audit events are inserted. MimDB creates the
current month's and next month's partitions on startup, and a background
goroutine re-runs the check every 24 hours. Without it, synchronous audit
writes would fail at a month boundary, rolling back every critical mutation.
The partition creation is idempotent (`CREATE TABLE IF NOT EXISTS`) and safe
to run repeatedly. The same mechanism maintains the partitions of
`_metering.events`, `_mimisbrunnr.request_log` and
`_metering.system_metrics`.
</Note>

No automatic retention is applied to `audit_log`. Drop old partitions
yourself if you need to bound its size.

## Metering

Per-project usage (request counts, storage bytes, connection counts) backs
`GET /v1/platform/projects/{projectID}/usage` and
`/usage/timeseries`. Request counts are buffered in memory and flushed to
`_metering.request_counts` every `[metering].flush_interval`; a snapshot of
storage and connection usage is written to `_metering.snapshots` hourly. A
daily job deletes rows from both tables that are older than
`[metering].retention_days`.

```toml
[metering]
flush_interval = "60s"
retention_days = 90
```

## Health probes

The `/health` and `/ready` endpoints are documented in detail on the
[Setup & Info](/platform/setup-and-info) page. Summary for orchestrators:

- Use `/health` as the **liveness probe** (Kubernetes `livenessProbe`).
  Returns `200` as long as the process is alive.
- Use `/ready` as the **readiness probe** (Kubernetes `readinessProbe`).
  Returns `503` if the database is unreachable.

### Kubernetes example

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 9000
  initialDelaySeconds: 5
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /ready
    port: 9000
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3
```

### Docker Compose health check

The included `docker-compose.yml` configures a health check against `/ready`:

```yaml
healthcheck:
  test: ["CMD-SHELL", "wget -qO- http://localhost:9000/ready || exit 1"]
  interval: 30s
  timeout: 5s
  start_period: 30s
  retries: 3
```

## Structured logging

MimDB outputs structured JSON logs to stdout. Each log line is a JSON object
with `time`, `level`, `msg` and additional context fields depending on the
log source; request-scoped lines carry `request_id`.

On bare-metal deployments with systemd, logs are captured by journald:

```bash
# Stream logs
journalctl -u mimdb -f

# JSON format (for Promtail, Filebeat, or Vector)
journalctl -u mimdb -f -o json

# Logs from the last hour
journalctl -u mimdb --since "1 hour ago" --no-pager
```

The default log level is `info`. Setting the environment variable
`LOG_LEVEL=debug` enables debug output; no other values are recognised.

## Monitoring subsystem

The in-process monitoring subsystem samples metrics into PostgreSQL,
evaluates component health, streams logs, evaluates alert rules and serves a
public status page. It is enabled with:

```toml
[monitoring]
enabled = true
node_id = "node-1"   # required
```

When disabled, none of the `/v1/platform/monitoring/*` routes are registered
and requests to them return `404`. All `/v1/platform/monitoring/*` endpoints
require operator access: the platform admin secret, or a dashboard user who
is an admin or owner of the organization that owns the dashboard project.

| Path | Purpose |
|------|---------|
| `GET /v1/platform/monitoring/health` | Per-component health as evaluated by this node |
| `GET /v1/platform/monitoring/metrics/timeseries` | Query stored samples from `_metering.system_metrics` |
| `GET /v1/platform/monitoring/metrics/catalog` | Names, units and types of every metric the sampler can store |
| `GET /v1/platform/monitoring/logs` | Cross-project log and audit timeline search |
| `GET /v1/platform/monitoring/logs/stream` | Server-Sent Events stream of new request log entries |
| `GET /v1/platform/monitoring/alerts/*` | Alert rules and events (see Alerting) |
| `GET /v1/status`, `/v1/status/history`, `/v1/status/uptime` | Public, unauthenticated, sanitized status data |
| `GET /status` | Embedded HTML status page |

Stored samples live in `_metering.system_metrics` (monthly partitions,
dropped after `system_metrics_retention_days`) and component status in
`_mimisbrunnr.component_status`.

Collectors are enabled under `[monitoring.collectors]`. The host collector
(CPU, memory, disk) is on by default. The Docker collector needs the Docker
socket mounted into the container (see the `docker-compose.monitoring.yml`
overlay). The DigitalOcean collector is described below.

## Log viewer

The log viewer provides real-time streaming and cross-project search
over the request log. Operators can tail errors live across every
project from the dashboard, and platform routes (those without a
`{ref}` in the URL) are captured under a `platform` sentinel so they
show up in the same timeline as project requests.

### SSE log streaming

`GET /v1/platform/monitoring/logs/stream` keeps the connection open and emits
one `event: log` event per matching request log entry. Each event payload is
a JSON object:

```
event: log
data: {"source":"request","project_ref":"abcd0123456789ef","timestamp":"2026-04-13T10:42:17Z","method":"POST","path":"/v1/auth/login","status":401,"duration_ms":42,"service":"auth","error_code":"AUTH-0001","request_id":"01HZQ..."}

```

Optional query parameters narrow the stream:

- `level=error|warn|info` - `error` matches HTTP 5xx, `warn` matches 4xx;
  any other value returns `SYS-0803`
- `service=auth` - filter to one logical service
- `project=<ref>` - filter to a single project, or `project=platform` for
  non-project requests

The timestamp is stamped when the entry reaches the stream, not at request
time. There is no buffered catch-up: subscribers receive events from the
moment they connect forward.

### Subscriber limits and slow-consumer behavior

The registry caps total active subscribers at `monitoring.max_sse_subscribers`
(default 20). Exceeding the cap returns `503` with `SYS-0806`; the client
should back off and retry. A connection that cannot stream returns
`SYS-0811`, and a subscription attempted during shutdown returns `SYS-0812`.

Per-subscriber buffering is bounded (64 entries). When a subscriber falls
behind and the buffer fills, new events for that subscriber are dropped
rather than blocking the request log writer. The metric sampler and the
request log writer never wait on subscribers, so a stalled dashboard cannot
back-pressure the rest of the system.

### Cross-project search

`GET /v1/platform/monitoring/logs` queries both `_mimisbrunnr.request_log`
and `_mimisbrunnr.audit_log` over the last 24 hours and merges the results
into a single timeline sorted by timestamp descending. Each entry includes
`source` (`request` or `audit`) and `project_ref`; audit entries additionally
carry `action`, `actor_id`, `actor_role` and `resource`.

Query parameters:

- `level=error|warn` - applies only to request log rows; audit rows are
  omitted when a level filter is set
- `limit` - max entries to return (default 100, hard cap 1000)

Example:

```bash
curl -s "https://api.example.com/v1/platform/monitoring/logs?level=error&limit=20" \
  -H "Authorization: Bearer $ADMIN_TOKEN" | jq '.entries[0]'
```

```json
{
  "source": "request",
  "project_ref": "abcd0123456789ef",
  "timestamp": "2026-04-13T10:42:17Z",
  "method": "POST",
  "path": "/v1/auth/login",
  "status": 500,
  "duration_ms": 105,
  "service": "auth",
  "error_code": "AUTH-0900"
}
```

This endpoint returns `{"entries": [...]}` directly, without the
`data`/`error`/`meta` envelope used by the rest of the platform API.

### What reaches the request log

The request log middleware records a request when any of these hold: the
status is 400 or higher, the request took longer than 500ms, or it is a
`POST`/`PUT`/`PATCH`/`DELETE` that returned 2xx and
`request_log.capture_successful_mutations` is `true` (the default). Two more
settings control the noise level:

1. **Platform sentinel.** Requests that have no `{ref}` URL parameter (for
   example `/v1/platform/organizations`) are logged with
   `project_ref = "platform"` when `request_log.platform_logging = true`.
   They land in the same `_mimisbrunnr.request_log` table and the same SSE
   stream, so a single dashboard view covers project and platform traffic.

2. **Skip paths.** A configurable list of exact URL paths is excluded from
   logging entirely (no usage count, no entry, no SSE broadcast). The
   default skip list is `/health`, `/ready`, `/metrics` - these are scraped
   by Docker health checks and Prometheus and would otherwise dominate the
   log volume.

```toml
[request_log]
platform_logging = true
skip_paths = ["/health", "/ready", "/metrics"]
```

Partitions older than `request_log.retention_days` (default 7) are dropped by
a background reaper. The per-project usage counter (the billing and quota
hook) is intentionally not incremented for the `platform` sentinel - only
real project refs count towards usage.

## Alerting

Alerts evaluate metric rules on a ticker (`evaluation_interval`, default
60s), persist hysteresis state to PostgreSQL, and dispatch notifications
through four channels: in-app, email, webhook, and ntfy. Each rule fires only
after two consecutive evaluations confirm a threshold crossing, and resolves
only after two consecutive evaluations confirm recovery. The counters are
persisted in `_mimisbrunnr.alert_state`, so a process restart cannot re-fire
an already-firing alert.

### Default rules

On first startup MimDB seeds ten rules with `is_default = true`. Every
default rule uses the `in_app` channel only so the rule set fires the
moment metrics arrive without requiring SMTP, webhook, or ntfy
configuration. Operators add additional channels via `PATCH` once those
destinations are set up.

| Rule                      | Metric                                    | Condition | Window | Severity  |
|---------------------------|-------------------------------------------|-----------|--------|-----------|
| High CPU                  | `host_cpu_percent`                        | `> 90`    | 5 min  | critical  |
| High memory               | `host_memory_percent`                     | `> 85`    | 5 min  | warning   |
| Disk full                 | `host_disk_used_percent`                  | `> 90`    | 1 min  | critical  |
| Pool exhaustion           | `db_pool_utilization`                     | `> 90`    | 2 min  | warning   |
| PG backend saturation     | `pg_server_backends_utilization`          | `> 75`    | 2 min  | warning   |
| High error rate           | `http_error_rate`                         | `> 10`    | 5 min  | critical  |
| Audit drops               | `audit_events_dropped_rate`               | `> 0`     | 1 min  | critical  |
| Pooler probe failing      | `mimdb_pooler_probe_healthy`              | `< 1`     | 3 min  | critical  |
| Pooler canary disconnects | `pooler_canary_disconnects`               | `> 3`     | 15 min | warning   |
| API latency high          | `mimdb_http_request_duration_seconds_p95` | `> 5`     | 10 min | warning   |

The derived metrics (`db_pool_utilization`, `pg_server_backends_utilization`,
`http_error_rate`, `audit_events_dropped_rate`, `pooler_canary_disconnects`)
are computed by the alert evaluator from raw gauges and counters written by
the metrics sampler - they do not appear as Prometheus metric names
themselves.

`API latency high` measures time spent inside the MimDB process only. An
external uptime check times the entire path - probe network, CDN edge, and
origin - so a degraded network segment and a slow server look identical to
it. Comparing an external check against this rule separates the two: if the
external check reports high latency while this rule stays clear, the delay
is in the network path rather than the server.

### Configuration

```toml
[monitoring.alerting]
enabled = true

# Optional. 0 or omitted = 60s.
evaluation_interval = "60s"

# SSRF allow-list. Webhook and ntfy URLs that resolve to private,
# loopback, or link-local IP space are rejected at rule create/patch
# time UNLESS the target IP falls inside one of these CIDR ranges.
# An empty list rejects every private destination. Whitelist your
# internal VPC CIDR if cross-node webhooks (e.g. to an Alertmanager
# inside the VPC) should work.
allowed_internal_cidrs = ["10.0.0.0/8"]
```

`[monitoring.alerting]` sits under the `[monitoring]` block, so disabling
`monitoring.enabled` also disables alerting. When alerting is disabled the
alert routes are not registered and return `404`. The
`allowed_internal_cidrs` field has no corresponding environment variable
because the config loader cannot split list values - it must be set in TOML
directly, the same constraint as `realtime.allowed_origins`.

### Channel configuration

Per-rule destinations live in each rule's `channel_config` JSON object. This
keeps routing decoupled from global config, so different rules can target
different destinations through the same channel kinds:

| Channel | Required keys in `channel_config`              |
|---------|------------------------------------------------|
| in_app  | *none - event is persisted to `alert_events`*  |
| email   | `email_to`                                     |
| webhook | `webhook_url`                                  |
| ntfy    | `ntfy_server` **and** `ntfy_topic`             |

The `ntfy` channel has no public-service fallback: both `ntfy_server` and
`ntfy_topic` must be present or the channel returns an error. Operators
who want a public `ntfy.sh` destination configure it explicitly. Email
notifications use the `[email]` SMTP settings; the content is HTML, and
user-supplied fields (rule name, event message, node ID) are escaped before
insertion into the template.

### SSRF allow-list semantics

When a rule is created or patched, every URL-bearing key in
`channel_config` (`webhook_url`, `ntfy_server`) is parsed, the hostname is
resolved, and each resolved address is checked:

1. If the address is public, accept.
2. If the address is loopback, private, link-local, or unspecified:
   - If it falls inside an entry in `allowed_internal_cidrs`, accept.
   - Otherwise, reject with HTTP 400 and error code `SYS-0809`.

### API

All alert endpoints sit under `/v1/platform/monitoring/alerts` and require
operator access:

| Method | Path              | Purpose                                   |
|--------|-------------------|-------------------------------------------|
| GET    | `/rules`          | List every rule regardless of `enabled`   |
| POST   | `/rules`          | Create a new rule (SSRF-validated)        |
| PATCH  | `/rules/{id}`     | Partial update (SSRF-validated)           |
| DELETE | `/rules/{id}`     | Idempotent delete (returns 204 on missing)|
| GET    | `/events`         | Most recent fire/resolve events (`limit`, default 100) |

`POST` and `PATCH` return the full updated rule row in the response body
so the dashboard stays consistent without a follow-up `GET`. Error codes:

| Code      | HTTP | Meaning                                       |
|-----------|------|-----------------------------------------------|
| SYS-0807  | 404  | Alert rule not found                          |
| SYS-0808  | 400  | Invalid request (JSON, fields, UUID)          |
| SYS-0809  | 400  | Channel config rejected by SSRF guard         |
| SYS-0810  | 500  | Alert store (database) unavailable            |

### Schema

Three tables in the `_mimisbrunnr` schema back alerting:

- `alert_rules` - durable rule definitions. `channels` is a `TEXT[]` of
  channel kinds; `channel_config` is `JSONB`; `window` is an `INTERVAL`.
  CHECK constraints enforce the enum values of `condition`, `scope`,
  `severity`, and `aggregation`.
- `alert_events` - append-only history of fire/resolve transitions,
  indexed by both `(rule_id, created_at DESC)` and `(created_at DESC)`.
  Cascades on rule delete.
- `alert_state` - per-`(rule_id, node_id)` hysteresis counters. Primary
  key is the composite of both columns so parallel evaluators on
  different nodes never collide. Cascades on rule delete.

## Cloud provider collectors

The monitoring subsystem supports cloud provider collectors that pull metrics
directly from the provider's API. Each collector is independent of the rest
of the stack: enabling or disabling one has no effect on the host, Docker,
or Prometheus collectors.

Cloud collectors are **off by default** and are opted into via
`[monitoring.collectors]`. Running a collector that targets infrastructure
you do not own wastes API quota and surfaces metrics the operator has no
way to act on, so MimDB refuses to guess.

### DigitalOcean

The DigitalOcean collector reads droplet-level CPU, memory, disk, and
bandwidth gauges from the DigitalOcean Monitoring API and emits them through
the normal sampler pipeline so they land in `_metering.system_metrics`
alongside every other metric. It monitors one droplet per process.

```toml
[monitoring.collectors]
digitalocean = true

[monitoring.digitalocean]
api_token = "dop_v1_..."
# droplet_id is optional. When omitted the collector queries the DO
# metadata service at 169.254.169.254/metadata/v1/id to auto-detect
# the host's droplet ID. Set it explicitly when running the process
# somewhere other than on the target droplet (e.g. a jump host that
# monitors a separate droplet remotely).
droplet_id = ""
```

#### Required: DO Monitoring agent

The DigitalOcean Monitoring endpoints only return data for droplets that
have the DigitalOcean Monitoring agent installed:

```bash
curl -sSL https://repos.insights.digitalocean.com/install.sh | sudo bash
```

Without the agent the collector's API calls return errors and the sampler
treats the collector as failed for that tick. The rest of the monitoring
stack continues unaffected, so a missing agent is a warning-level condition,
not a hard failure.

#### Metrics emitted

| Metric                           | Unit    | Meaning                                                           |
|----------------------------------|---------|-------------------------------------------------------------------|
| `do_droplet_cpu_percent`         | percent | `(total - idle) / total` across every CPU mode in the last sample |
| `do_droplet_memory_used_bytes`   | bytes   | `total - available` from the droplet's memory report              |
| `do_droplet_memory_total_bytes`  | bytes   | Total memory reported by the droplet                              |
| `do_droplet_disk_used_percent`   | percent | `(size - free) / size` for the root filesystem                    |
| `do_droplet_bandwidth_in_bytes`  | bytes   | Most recent sample of public-interface inbound bandwidth          |
| `do_droplet_bandwidth_out_bytes` | bytes   | Most recent sample of public-interface outbound bandwidth         |

Every sample carries a `droplet_id` label so dashboards can filter by
host. The metric catalog registers all six entries at startup, so they
appear in the `/metrics/catalog` response used by dashboard metric
pickers.

#### Graceful degradation

Two independent failure modes are handled at startup without crashing
the process:

1. **Non-DigitalOcean host.** When `droplet_id` is unset and the metadata
   service is unreachable (e.g. a local dev machine), the collector is
   skipped with a warning log and the sampler continues with the remaining
   collectors.
2. **Missing API token.** When `api_token` is empty the collector cannot
   authenticate, so it is skipped with a warning log even if auto-detect
   succeeded.

In both cases the process starts successfully; operators see the skip
reason in the startup log and can act on it without a restart loop.
