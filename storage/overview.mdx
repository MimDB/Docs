# Storage

MimDB Storage provides S3-style object storage with metadata in PostgreSQL.
Files are organized into **buckets**, uploaded via a simple HTTP endpoint or
the resumable tus protocol, and served with range request support.

## Storage backends

Where the bytes live is a deployment choice made by the operator in the
`[storage]` section of the server configuration:

- **`localfs`** (default) - files are stored on the server's own filesystem
  under `local_path`.
- **`r2`** - files are stored in Cloudflare R2. Public MimDB buckets map to an
  R2 bucket configured for CDN access and private buckets to a separate
  private R2 bucket.

The API is identical on both backends. Bucket and object metadata (paths,
sizes, content types, ETags, ownership) always lives in PostgreSQL, in the
`_storage` schema.

## Object lifecycle

Every object moves through a defined set of states:

```
Upload started
      |
      v
  [pending]  --- upload completes --->  [active]  --- DELETE --->  [deleted]
      |                                                                |
      |  pending_ttl expires                         file removed in the
      v                                              background
  removed
```

- **pending** - created when an upload starts. The path is reserved: another
  upload to the same path is refused with `409 STOR-0301` until this one
  completes or is removed. Pending objects that are not completed within
  `pending_ttl` (default: 24h) are removed automatically.
- **active** - the upload completed; the object is available for download and
  appears in object listings.
- **deleted** - soft-deleted via the API. The object is no longer downloadable
  or listed, and its path is free for a new upload straight away. The bytes
  are removed by a background cleanup that runs every `reaper_interval`
  (default: 1h).

<Note>
Deletion is always soft: `DELETE` returns as soon as the object is marked
`deleted`. Objects in the `deleted` state are not accessible for download,
even though their bytes may still exist on the backend for a short while.
</Note>

## Authentication

Different operations require different credential levels:

| Operation | Required credential |
|-----------|-------------------|
| Create / delete / update buckets | `service_role` key |
| List buckets | `service_role` key |
| Upload objects | JWT or API key (project-scoped) |
| Replace / delete objects | The uploader's JWT, or `service_role`; any JWT in a `shared` bucket (see [Who can change an object](/storage/buckets#who-can-change-an-object)) |
| Download from private bucket | JWT or API key |
| Download from public bucket | None (anonymous) |
| Generate signed URL | JWT or API key |

The `service_role` key is the application's own credential: it can manage
buckets and change any object regardless of who uploaded it. Use it only in
trusted server-side code, never in client-side applications.

Credentials are sent in one of two headers:

| Credential | Header |
|------------|--------|
| User JWT (from `/v1/auth`) | `Authorization: Bearer <access_token>` |
| API key (`anon` or `service_role`) | `ApiKey: <key>` |

"API key" in the table above means the `service_role` key. The `anon` key
identifies the caller as anonymous, and anonymous callers cannot use any
`/object/`, `/sign/` or `/upload/` route: a read returns `404 STOR-0203`, a
write returns `401 STOR-0109`. Anonymous downloads are served only from the
`/public/` endpoint of a public bucket, or through a signed URL. An API key
placed in the `Authorization: Bearer` header is not accepted as a JWT; put it
in `ApiKey` instead.
