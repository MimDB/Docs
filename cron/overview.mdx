# Scheduled Jobs

Scheduled jobs let you run SQL statements on a recurring cron schedule inside your project's database. Each job runs in that database as the project's `{ref}_service` role with `search_path` set to `public`, so it has full access to your tables with no additional configuration.

## What is pg_cron

pg_cron is a PostgreSQL extension that executes SQL commands on a time-based schedule, managed entirely inside the database. There is no external scheduler process to deploy or monitor - jobs run as long as PostgreSQL is running.

MimDB wraps pg_cron with per-tenant isolation: pg_cron's metadata lives in the platform database, and each job is scheduled with `cron.schedule_in_database()` so it executes in the owning project's database under that project's service role. Jobs are stored under the internal name `{ref}_{name}` and every read is filtered by the owning role, so one project's jobs are invisible to another.

## Enabling pg_cron

pg_cron requires two changes to `postgresql.conf` before it can be used:

```ini
shared_preload_libraries = 'pg_cron'
cron.database_name = 'mimisbrunnr'   # the MimDB platform database, not a project database
```

Both changes require a PostgreSQL server restart. Once pg_cron is installed, enable it in `config.toml`:

```toml
[extensions.pg_cron]
enabled = true
max_jobs_per_project = 50   # max scheduled jobs per tenant
min_interval_seconds = 60   # minimum allowed schedule interval
max_command_length = 4096   # max SQL command length in bytes
job_timeout_seconds = 60    # statement_timeout applied per execution
lock_timeout_seconds = 10   # lock_timeout applied per execution
```

<Note>
The minimum schedule interval is 60 seconds by default. MimDB computes the shortest gap between consecutive runs from the minute field (and from the hour field when the minute field is a single value) and rejects expressions below `min_interval_seconds` with `CRON-0004: Schedule interval below minimum allowed`. `* * * * *` runs every 60 seconds and is therefore accepted at the default; raise `min_interval_seconds` to forbid it.
</Note>

## Limits

| Limit | Default | Config key |
|-------|---------|------------|
| Max jobs per project | `50` | `max_jobs_per_project` |
| Minimum interval | `60` seconds | `min_interval_seconds` |
| Max command length | `4096` bytes | `max_command_length` |
| Statement timeout per execution | `60` seconds | `job_timeout_seconds` |
| Lock timeout per execution | `10` seconds | `lock_timeout_seconds` |

The job and lock timeouts are injected as `SET LOCAL` preambles before each execution, so they apply per-run and do not leak into the connection pool. Changing them in `config.toml` affects jobs created afterwards; existing jobs keep the preamble they were stored with until they are updated.

## SQL validation

Before storing a job, MimDB validates the SQL command against a deny-list of patterns that could escalate privileges or interfere with the tenant isolation model:

<Warning>
The following SQL patterns are denied in scheduled job commands (matching is case-insensitive):

- `SET ROLE` - prevents switching to a different database role
- `SET SESSION AUTHORIZATION` - prevents changing session identity
- `SET search_path` - MimDB injects the correct search_path automatically
- `ALTER SYSTEM` - prevents server-wide configuration changes
- `COPY ... TO`, `COPY ... FROM`, `COPY ... PROGRAM` - prevents file and OS command access (every `COPY` is rejected)
- `CREATE EXTENSION`, `DROP EXTENSION` - extension management goes through the extensions endpoints
- `dblink`, `dblink_connect`, `postgres_fdw`, `file_fdw`, `CREATE SERVER`, `CREATE USER MAPPING`, `IMPORT FOREIGN SCHEMA` - no foreign-data or cross-database access
- `lo_import`, `lo_export` - no large-object filesystem access

Commands that match these patterns are rejected with `CRON-0006: SQL command contains denied pattern`. Commands longer than `max_command_length` are rejected with `CRON-0005`. The deny-list uses word boundaries, so table names like `copy_logs` are not affected, but the same words inside comments or string literals will still trigger it.
</Warning>

The deny-list is a defense-in-depth guardrail. The actual security boundary is the PostgreSQL role: each job runs under the project's service role, which has no superuser privileges and no access to other projects' databases.
