# Migrations

MimDB separates two migration concerns: **platform migrations** that run at
server startup and keep the platform's own schema up to date, and **custom SQL**
that you run against your project's database using the SQL execution endpoint.

## Platform migrations

Platform migrations are embedded in the server binary and applied automatically
on every startup, in sequential order, against the platform database. Each
applied file is recorded in `_mimisbrunnr.schema_migrations`, so a restart or
upgrade only runs the files that have not been applied yet. No manual
intervention is required.

<Note>
Platform migrations are idempotent. Restarting the server after a failed
migration or an upgrade is always safe; already-applied migrations are
skipped.
</Note>

Platform migrations manage the platform database only: organizations, projects,
API keys and signing keys, storage and metering metadata, audit and request
logs, monitoring, and the shared roles used by the REST engine and connection
pooler. They never touch the tables inside your project database.

## Project provisioning

When a new project is created, MimDB creates a dedicated PostgreSQL database
named after the project ref and provisions it in a single transaction:

- the contrib extensions `pgcrypto`, `pg_trgm`, `uuid-ossp`, and `moddatetime`
- an `extensions` schema with Supabase-compatible wrappers such as
  `extensions.uuid_generate_v4()`
- the `auth` schema with the RLS helper functions (`auth.uid()`, `auth.role()`,
  `auth.jwt()`, `auth.email()`, `auth.app_metadata()`, `auth.user_metadata()`)
- the `_mimisbrunnr` schema holding two DDL event triggers: one that enables
  row-level security on every new table in `public`, and one that notifies the
  REST engine so its schema cache is refreshed
- the three project roles `{ref}_anon`, `{ref}_authenticated`, and
  `{ref}_service`, plus the login role used for direct connections
- the tenant template (below), followed by grants and default privileges for
  the three roles

The auto-RLS trigger is re-applied at every server start, so it always matches
the running server.

## Tenant template

The tenant template provisions the initial objects every project needs before
any application tables are created:

- `auth_users` - user accounts with email, phone, display name, and metadata
- `auth_refresh_tokens` - refresh tokens with family-based reuse detection
- `auth_identities` - OAuth provider identities linked to users
- `auth_password_resets` - password reset tokens
- `auth_sessions` - active session tracking with device metadata
- RLS enabled on all auth tables
- `SELECT` policies on `auth_users`, `auth_identities`, and `auth_sessions`
  that limit the `{ref}_authenticated` role to its own rows; no policies at all
  on `auth_refresh_tokens` and `auth_password_resets`
- All privileges on the auth tables revoked from the `anon` and `authenticated`
  roles, so end users reach their profile only through `/v1/auth/{ref}/user`
  and never through the REST API

Your application tables are separate from these. The auth tables are managed by
MimDB's auth subsystem; you create your own tables independently using the SQL
execution endpoint.

## Custom SQL

The `POST /v1/sql/{ref}/execute` endpoint runs SQL against your project
database. It requires the `service_role_key` and executes exactly one statement
per request.

<CodeGroup>
```bash Single statement
curl -X POST http://localhost:9000/v1/sql/<ref>/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <service_role_key>" \
  -d '{
    "query": "CREATE TABLE events (id uuid primary key default gen_random_uuid(), name text not null, payload jsonb, occurred_at timestamptz not null default now())"
  }'
```

```bash Parameterized query
curl -X POST http://localhost:9000/v1/sql/<ref>/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <service_role_key>" \
  -d '{
    "query": "INSERT INTO events (name, payload) VALUES ($1, $2)",
    "params": ["user.created", {"user_id": "abc123"}]
  }'
```

```bash Several statements atomically
curl -X POST http://localhost:9000/v1/sql/<ref>/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <service_role_key>" \
  -d '{
    "query": "DO $$ BEGIN ALTER TABLE events ADD COLUMN source text; ALTER TABLE events ADD COLUMN severity text NOT NULL DEFAULT '"'"'info'"'"'; END $$"
  }'
```
</CodeGroup>

**Limits and behavior:**

| Property | Value |
|----------|-------|
| Maximum query size | 64 KB (`SQL-0003`) |
| Statement timeout | 30 seconds (`SQL-0005`, HTTP 408) |
| Maximum result rows | 10,000 (result is truncated, not errored) |
| Statements per request | 1 - a `BEGIN; ...; COMMIT;` string is rejected with `SQL-0004` |
| `search_path` | `public, auth` for every execution |
| Role | `{ref}_service` - RLS is not enforced |

Each request runs in its own transaction: the statement is committed if it
succeeds and rolled back if it fails, so a failed statement never leaves a
partial change behind. The timeout is applied with `SET LOCAL statement_timeout`
inside that transaction, so it reverts cleanly when the connection returns to
the pool.

Use parameterized queries (`$1`, `$2`, ...) when inserting user-supplied values
to prevent SQL injection. The `params` array maps positionally to the
placeholders in the query string; send values destined for `numeric` columns as
JSON strings (`"12.50"`). See [SQL Execution](/sql/execution) for the full
result format and error codes.

## Best practices

<Warning>
Destructive migrations (`DROP TABLE`, `DROP COLUMN`, `TRUNCATE`) cannot be
rolled back once committed. Always take a database backup before running them
in production.
</Warning>

- **Version your migrations.** Keep migration SQL in numbered files in your
  application repository (e.g., `0001_create_events.sql`). Apply them in order
  and track which have run in a `schema_migrations` table.

- **Test on staging first.** Run every migration against a staging project
  before applying it to production. Schema errors are far cheaper to debug
  before they touch real data.

- **Group related DDL in a `DO` block.** The endpoint accepts one statement per
  request, and a `DO $$ ... $$` block counts as one. Everything inside it runs
  in the request's transaction, so a failure midway leaves the schema unchanged
  rather than partially modified.

- **Avoid long-held locks.** Operations like `ALTER TABLE ... ADD COLUMN NOT NULL`
  without a default lock the table for the duration. On large tables, use
  `ADD COLUMN` with a default first, then backfill, then add the constraint
  separately.
