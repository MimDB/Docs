# Database

Every MimDB project gets its own dedicated PostgreSQL database. Tables you
create in that database are immediately available as REST endpoints through
MimREST, the PostgREST-compatible REST engine - no extra configuration required.

## Multi-tenant architecture

MimDB uses **one PostgreSQL database per project**. When you create a project
with ref `ca1deb46032e8010`, the platform provisions a database with that name
and three PostgreSQL roles scoped to it:

| Role | Purpose |
|------|---------|
| `ca1deb46032e8010_anon` | Unauthenticated requests. Subject to RLS. `SELECT` on tables and sequences, `EXECUTE` on functions; no write privileges unless you grant them per table. |
| `ca1deb46032e8010_authenticated` | JWT-bearing requests. Subject to RLS. `SELECT`, `INSERT`, `UPDATE`, `DELETE` on all tables. |
| `ca1deb46032e8010_service` | Service role. Owns the tables, holds `CREATE` on the `public` schema, and has `BYPASSRLS`. |

The grants above are also set as default privileges, so tables you create later
receive the same grants automatically.

All user tables live in the `public` schema of the project database. Every
data-plane request that reads or writes rows (`/v1/rest/`, `/v1/realtime/`,
`/v1/sql/`, `/v1/vectors/`) runs inside a transaction where `SET LOCAL ROLE` is
applied from the JWT claim or API key. Because each project has its own database,
one project can never read or write rows in another project's database.

RLS helper functions (`auth.uid()`, `auth.role()`, `auth.jwt()`, `auth.email()`)
are installed in the `auth` schema of each project database, and a DDL event
trigger enables Row Level Security on every table created in `public` (see
[Enabling RLS](/auth/row-level-security#enabling-rls) for what a new table
looks like to each role).

Each project database also ships with the `pgcrypto`, `pg_trgm`, `uuid-ossp`,
and `moddatetime` extensions installed, and an `extensions` schema containing
wrapper functions (`extensions.uuid_generate_v4()`, `extensions.gen_random_uuid()`)
so schemas exported from Supabase work unchanged.

<Note>
The platform's own management tables live in the `_mimisbrunnr` schema of the
platform database. Project databases contain only a small `_mimisbrunnr` schema
holding the trigger functions described above; neither is exposed through the
REST API or the SQL endpoint.
</Note>

## Schema introspection

MimDB exposes two read-only introspection endpoints that query PostgreSQL
system catalogs (`pg_class`, `pg_attribute`, `pg_constraint`, `pg_index`,
`information_schema.columns`). Both require a `service_role` key and list
regular and partitioned tables in the `public` schema (views are not included).

### List tables

```bash
curl http://localhost:9000/v1/introspect/<ref>/tables \
  -H "ApiKey: <service_role_key>"
```

```json
{
  "data": [
    {
      "name": "todos",
      "schema": "public",
      "row_estimate": 42,
      "row_count_exact": true,
      "size_bytes": 8192,
      "comment": null
    }
  ],
  "error": null,
  "meta": { "request_id": "01970000-0000-7000-8000-000000000000" }
}
```

`row_estimate` is an exact `count(*)` (and `row_count_exact` is `true`) for
tables whose planner estimate is below 100,000 rows, provided the count finishes
within 150 ms (500 ms on the detail endpoint). Otherwise it is the planner
estimate from `pg_class.reltuples` and `row_count_exact` is `false`.
`size_bytes` is `pg_total_relation_size`, which includes indexes and TOAST.

### Get table detail

```bash
curl http://localhost:9000/v1/introspect/<ref>/tables/todos \
  -H "ApiKey: <service_role_key>"
```

```json
{
  "data": {
    "name": "todos",
    "schema": "public",
    "columns": [
      {
        "name": "id",
        "type": "bigint",
        "nullable": false,
        "default_value": null,
        "is_primary_key": true,
        "comment": null,
        "ordinal_position": 1
      },
      {
        "name": "task",
        "type": "text",
        "nullable": false,
        "default_value": null,
        "is_primary_key": false,
        "comment": null,
        "ordinal_position": 2
      }
    ],
    "primary_key": ["id"],
    "foreign_keys": [],
    "indexes": [
      {
        "name": "todos_pkey",
        "columns": ["id"],
        "is_unique": true,
        "is_primary": true,
        "type": "btree"
      }
    ],
    "row_estimate": 42,
    "row_count_exact": true,
    "size_bytes": 8192,
    "comment": null
  },
  "error": null,
  "meta": { "request_id": "01970000-0000-7000-8000-000000000001" }
}
```

Column `type` is the SQL-standard name from `information_schema.columns`
(`bigint`, `integer`, `boolean`, `numeric`, `timestamp with time zone`, `uuid`),
not the PostgreSQL internal alias (`int8`, `bool`, `timestamptz`). Each entry in
`foreign_keys` has `name`, `columns`, `foreign_schema`, `foreign_table`, and
`foreign_columns`; composite keys list several columns in matching order.

## How the REST API exposes tables

MimREST reads the project database's catalog into a per-project schema
cache. Every table, partitioned table, view, and materialized view in the
`public` schema becomes a REST endpoint under `/v1/rest/{ref}/`:

- **Tables** map to `/v1/rest/{ref}/{table_name}`
- **Views** are exposed the same way as tables
- **Stored functions** are callable via `/v1/rest/{ref}/rpc/{function_name}`

Row Level Security policies are enforced automatically. The `anon` role sees
only rows permitted by your RLS policies; the `service_role` key bypasses RLS
entirely.

<Note>
Schema changes (new tables, added columns, dropped indexes) take effect as soon
as the schema cache is refreshed. A DDL event trigger in every project database
sends a `NOTIFY` on each DDL statement, and MimREST invalidates the
cache for that project when it receives it, so changes made through the SQL
endpoint are normally visible on the next request. The cache also expires on its
own every 5 minutes (`[rest_engine].schema_cache_ttl`) as a fallback.
</Note>
