# Connection Strings

MimDB can expose direct PostgreSQL access to your project's database through a
managed connection pooler. This is useful for running migrations, analytics
queries, ORMs, or any tooling that needs a real PostgreSQL connection rather
than the REST API.

## Connection info

`GET /v1/platform/projects/{id}/connection-info`

Returns the connection parameters for a project: the REST and realtime
endpoint URLs derived from `[server].base_url`, and the pooled database
connections when a pooler is configured. Requires `admin` or `owner`
membership in the project's organization (or the admin secret).

<CodeGroup>
```bash Request
curl http://localhost:9000/v1/platform/projects/01970000-0000-7000-8000-000000000002/connection-info \
  -H "Authorization: Bearer <access_token>"
```

```json Response
{
  "data": {
    "project_ref": "ca1deb46032e8010",
    "schema_name": "public",
    "api_url": "https://api.example.com/v1/rest/ca1deb46032e8010",
    "realtime_url": "wss://api.example.com/v1/realtime/ca1deb46032e8010",
    "db_session": {
      "host": "db.example.com",
      "port": 5432,
      "database": "ca1deb46032e8010",
      "user": "032e8010ca1deb46"
    },
    "db_transaction": {
      "host": "db.example.com",
      "port": 6543,
      "database": "ca1deb46032e8010",
      "user": "032e8010ca1deb46"
    }
  },
  "error": null,
  "meta": { "request_id": "01970000-0000-7000-8000-000000000040" }
}
```
</CodeGroup>

| Field | Present when |
|-------|--------------|
| `api_url`, `realtime_url` | `[server].base_url` is set (always, in practice) |
| `db_session` | The pooler is enabled (`[pgdog].binary_path` set, which also makes `[pgdog].public_host` required) and `pooling_mode` is `per_project_role` |
| `db_transaction` | The pooler is enabled and `[pgdog].transaction_port` is non-zero |

`user` is the project's login role - the secret half of the project's UUIDv8.
The response never includes the password: it is shown once in
`db_connection_string` at project creation (when `[database].direct_host` is
configured) and again after each credential rotation.

## The pooler

MimDB runs the pooler as supervised child processes. Each port can be served
by PgDog (the default) or PgBouncer, selected per port with
`[pgdog].session_engine` and `transaction_engine`.

In the default pooling mode (`per_project_role`), each project gets its own
dedicated PostgreSQL database and a login role (the secret half of the
UUIDv8-derived ref) with a unique SCRAM-SHA-256 credential. With PgDog,
clients authenticate directly to PostgreSQL through the pooler using that
credential - no credential tables or auth queries are needed. With PgBouncer,
the pooler looks the role's stored SCRAM secret up with `auth_query` and logs
in on the client's behalf; the backend still runs as the tenant's own role.

Two pooler ports have different semantics:

- **Port 5432 - session pooler.** Each client connection is pinned to one
  server backend for the entire session. Use this when your client needs
  `LISTEN`/`NOTIFY`, advisory locks, named cursors, session-scoped `SET`
  statements, or any other behaviour that requires server-side session
  state to persist between queries.

- **Port 6543 - transaction pooler.** Server backends are returned to the
  pool between transactions, so a small pool can serve many concurrent
  clients. Use this for application servers, microservices, edge functions
  and any short-lived workload that does not depend on session state.

The ports are configurable (`[pgdog].port` and `transaction_port`); the
connection info response always reports the configured values.

## Rotate credentials

`POST /v1/platform/projects/{id}/rotate-db-credential`

Generates a new 64-character hex password for the project's login role and
applies it with `ALTER ROLE`. The password is never stored; it is returned
once, on its own and embedded in a connection string for the project's
database through the session pooler (or the transaction pooler when no
session pooler is configured). All existing connections using the old
password will need to reconnect with the new one. Requires `admin` or `owner`
membership (or the admin secret).

<CodeGroup>
```bash Request
curl -X POST http://localhost:9000/v1/platform/projects/01970000-0000-7000-8000-000000000002/rotate-db-credential \
  -H "Authorization: Bearer <access_token>"
```

```json Response
{
  "data": {
    "db_connection_string": "postgresql://032e8010ca1deb46:a3f9...@syd1.example.com:5432/a1b2c3d4e5f67890?sslmode=require",
    "db_user": "032e8010ca1deb46",
    "db_password": "a3f9..."
  },
  "error": null,
  "meta": { "request_id": "01970000-0000-7000-8000-000000000041" }
}
```
</CodeGroup>

`db_connection_string` is empty when no pooler host is configured; `db_user`
and `db_password` are always returned, so the credential can be combined with
the host, port and database from the connection-info endpoint (the database
is always the project `ref`).

<Warning>
Credential rotation is immediate and irreversible. All active connections using
the old password will fail authentication after the rotation. Update your
connection strings before rotating in production, or coordinate a brief
reconnection window with your application.

The new password is only returned when the pooler is configured
(`[pgdog].public_host` set). On an instance without a pooler the response
contains an empty `db_connection_string` and the new password cannot be
recovered - do not call this endpoint there.

In `service_role` pooling mode the endpoint returns `POOL-0013` (501); there
is no per-project credential to rotate.
</Warning>

## Connection string format

Build a standard `postgresql://` URI from the connection info response:

```
postgresql://{user}:{password}@{host}:{port}/{ref}?sslmode=require
```

- `{user}` - the login role from `db_session.user`
- `{password}` - the credential shown at creation or after a rotation
- `{ref}` - the 16-character project ref, which is also the database name
- Tables live in the `public` schema; the login role's default `search_path`
  is `public`, so no `search_path` configuration is needed

Example with values filled in:

```
postgresql://032e8010ca1deb46:a3f9...@db.example.com:5432/ca1deb46032e8010?sslmode=require
```

`sslmode=require` is mandatory when connecting through the pooler in
production. The pooler uses passthrough authentication - your password
travels from your client to the pooler in plaintext inside the TLS session
before being forwarded to PostgreSQL as a SCRAM-SHA-256 exchange. Without TLS,
the password is exposed in transit, which is why the server refuses to start a
pooler with passthrough authentication unless `tls_client_required = true`.

## Direct vs pooled

| | Session pooler (:5432) | Transaction pooler (:6543) | Direct (PostgreSQL) |
|--|------------------------|----------------------------|---------------------|
| **Backend assignment** | One backend pinned per client session | Backend returned to pool between transactions | One backend per client |
| **Concurrency** | Limited by `session_default_pool_size` per (database, user) | High - small pool serves many clients | Limited by `max_connections` |
| **Session features** | Yes - `LISTEN`/`NOTIFY`, advisory locks, session `SET` | No - server state not preserved between transactions | Yes |
| **Best for** | Long-lived workers, realtime subscribers, batch jobs | App servers, microservices, edge functions | Migrations, `pg_dump`, analytics |
| **Availability** | When the pooler is enabled | When `[pgdog].transaction_port` is non-zero | When `[database].direct_host` is configured; the host and port appear only in the creation-time `db_connection_string` |

Pick the session pooler by default - it is safe for every workload. Move your
application to the transaction pooler when you have measured backend
exhaustion under load and the application code does not rely on
session-scoped state. Prepared statement handling on the transaction pooler
follows `[pgdog].prepared_statements` (`extended` by default).

Use the direct connection for database management tools (`psql`, `pg_dump`,
migration frameworks) and long-running analytics that hold connections beyond
the pooler's idle timeout.

### Idle-connection lifecycle

The pooler closes client sessions that have been idle for longer than
`[pgdog].client_idle_timeout` (default 1 hour), and clients that have held an
open transaction without a query for longer than
`client_idle_in_transaction_timeout` (default 5 minutes). After
disconnection, your client must reconnect to acquire a fresh backend.
Long-running batch jobs that block for more than an hour between queries
should send a periodic `SELECT 1` or use the direct connection instead.
