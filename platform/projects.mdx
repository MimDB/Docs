# Projects

A project is the core multi-tenant unit in MimDB. Each project gets its own
PostgreSQL database, authentication tables, JWT signing key, API keys,
storage signing key, and PostgreSQL roles. Everything project-scoped - REST
API, auth, realtime, storage - operates within that isolation boundary.

All project endpoints require platform authentication (the admin secret or a
platform user's access token). A platform user must be a member of the
organization that owns the project to read it, and an `admin` or `owner` to
create projects or use the credential, key and settings endpoints. Admin
secret callers bypass the membership checks.

## Create a project

`POST /v1/platform/projects`

Request body: `org_id` (UUID, required) and `name` (required).

Creating a project triggers the full provisioning sequence:

1. Generates a 16-character hex `ref` derived from a UUIDv8 (e.g., `ca1deb46032e8010`).
   The first character is always `a`-`f`, so a ref is never mistaken for a number.
2. Commits the project row with status `provisioning`, generates an HS256 JWT
   signing key stored in `_mimisbrunnr.jwt_signing_keys`, derives the `anon`
   and `service_role` API keys from it, and generates a storage signing key
   for signed URLs
3. Creates a dedicated PostgreSQL database named after the `ref`
4. Inside that database: installs the contrib extensions `pgcrypto`,
   `pg_trgm`, `uuid-ossp` and `moddatetime` (skipped with a warning if the
   server lacks them), applies the RLS
   helper functions and the automatic-RLS and schema-change event triggers,
   creates the roles `{ref}_anon`, `{ref}_authenticated` and `{ref}_service`
   (the service role has `BYPASSRLS`), creates the login role, and applies
   the tenant template (auth tables and policies) in the `public` schema
5. Provisions a random SCRAM password for the login role and records the
   role name in `_mimisbrunnr.db_credentials`
6. Sets the project status to `active`, makes the ref routable immediately,
   and reloads the connection pooler's routing table when a pooler is
   configured

The login role is named after the secret half of the project's UUIDv8 (the
16 hex characters that are not part of the public `ref`), so the internal
role names never appear in client connection strings. It is a member of
`{ref}_service`.

Provisioning is a three-phase sequence:

- **Phase A - Metadata commit:** The project row (status `provisioning`),
  signing keys and API key records are committed to the platform database
  under a platform-wide advisory lock, so concurrent creations serialise.
- **Phase B - Database creation:** `CREATE DATABASE`, then a single
  transaction in the new database applies extensions, RLS helpers, triggers,
  roles, the login role and the tenant template.
- **Phase C - Activation:** The project status is set to `active` and the
  lock is released.

If Phase B or Phase C fails, the newly created database is dropped and the
project status is set to `failed`. A project that is left in `provisioning`
by a crash between phases is reconciled on the next startup: activated if its
database exists and is complete, otherwise cleaned up and marked `failed`.
You will never end up with a partially-provisioned project serving traffic.

later - save it immediately, or use
[credential rotation](/platform/connection-strings) to obtain a new one.

## Get project

`GET /v1/platform/projects/{projectID}`

Retrieves a project by its UUID. Use the `id` from the create response (not
the `ref`).

<CodeGroup>
```bash Request
curl http://localhost:9000/v1/platform/projects/01970000-0000-7000-8000-000000000002 \
  -H "Authorization: Bearer <access_token>"
```

```json Response
{
  "data": {
    "id": "01970000-0000-7000-8000-000000000002",
    "org_id": "01970000-0000-7000-8000-000000000001",
    "ref": "ca1deb46032e8010",
    "name": "My App",
    "schema_name": "public",
    "database_name": "ca1deb46032e8010",
    "region": "",
    "status": "active",
    "settings": {},

  },
  "error": null,
  "meta": { "request_id": "01970000-0000-7000-8000-000000000006" }
}
```
</CodeGroup>

## Other project endpoints

All of these take the project UUID and require `admin` or `owner` membership
(or the admin secret):

| Endpoint | Purpose |
|----------|---------|
| `GET /api-keys`, `POST /api-keys/regenerate` | [Project API Keys](/platform/api-keys) |
| `GET /connection-info`, `POST /rotate-db-credential` | [Connection Strings](/platform/connection-strings) |
| `POST /sync-grants` | Re-apply object ownership and the standard grants in the project database (useful after a restore) |
| `GET /extensions`, `POST /extensions/{name}/toggle` | Per-project PostgreSQL extensions |
| `GET /rls/tables`, `POST /rls/tables/{table}/toggle`, `.../policies` | Row-level security management |
| `GET` and `POST /auth/providers`, `PUT` and `DELETE /auth/providers/{provider}` | OAuth provider configuration |
| `GET` and `POST /custom-domains`, `DELETE /custom-domains/{domainID}`, `POST /custom-domains/{domainID}/verify` | Custom domains (when `[custom_domains]` is enabled) |

Members of any role can read `GET /logs`, `GET /usage` and
`GET /usage/timeseries`.

## Project ref vs project ID

MimDB uses two distinct identifiers for every project:

| Identifier | Format | Used in |
|------------|--------|---------|
| `id` | UUID v7 (e.g., `01970000-0000-7000-8000-000000000002`) | Platform management endpoints (`/v1/platform/projects/{id}/...`) |
| `ref` | 16-character hex derived from UUIDv8 (e.g., `ca1deb46032e8010`) | Data plane API routes (`/v1/rest/{ref}/`, `/v1/auth/{ref}/`, `/v1/realtime/{ref}`, etc.), database name, role name prefix |

<Note>
The `ref` is embedded in JWT API keys as the `aud` (audience) claim. This is
how the auth cascade knows which project's signing key to use when validating a
token. The `ref` also serves as the PostgreSQL database name and the prefix for
all project-scoped roles (e.g., `{ref}_anon`, `{ref}_service`). The `id` (UUID)
is the internal primary key used for database relations. Keep both - you need
the `ref` for day-to-day API calls and the `id` for platform management
operations.
</Note>

## Project status

| Status | Meaning |
|--------|---------|
| `provisioning` | Database, roles, and keys are being created. The project is not routable and is hidden from organization project listings. |
| `active` | Fully provisioned. All API endpoints are operational. Only `active` projects are routable on the data plane. |
| `paused` | Accepted by the schema and listed by the organization endpoint, but not routable. No API sets this status. |
| `failed` | Provisioning failed partway through and the database was dropped. Hidden from listings; create a new project. |
| `deleted` | Accepted by the schema; excluded from listings, routing and the per-organization project count. No API sets this status. |

In practice, provisioning is synchronous - a successful `POST /v1/platform/projects`
response means the project is already `active`.

<Warning>
There is no API endpoint to delete or pause a project. Removing a project is
an operator task performed directly against PostgreSQL; dropping the project
database destroys all tables, data and auth users in it.
</Warning>
